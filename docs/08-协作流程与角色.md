# 协作流程与角色（2026-11-09 更新）

> 本文件说明 shikar 项目各类工作由谁负责。**产品设计与代码审核使用 Codex。**

## 角色分工
| 工作 | 负责方 | 说明 |
|---|---|---|
| **产品设计**（PRD / 信息架构 / 交互 / 原型） | **Codex** | 由协调会话调用 Codex CLI（只读评审）产出方案，整理进 `docs/` |
| **代码审核（Code Review）** | **Codex（在独立 review 会话中执行）** | 每条 PR 开一个独立的「代码审核」会话（与开发会话并列、可在 session 列表看到），在该会话中调用 Codex 审核，结论写入 `docs/`，问题回传开发会话修复 |
| 功能实现 | SuperAgent 开发者（`workbuddy/deepseek-v4-pro`） | 在独立 worktree 实现、开 PR |
| 架构评审 | 架构师（`workbuddy/glm-5.3`） | 技术方案 |
| 测试 | 测试员（`workbuddy/minimax-m3.1-flash`） | 用例与回归 |
| 产品验收 | （`agentrouter/gpt-6.1-sol`） | 必须基于真实运行结果 |
| 协调 | 协调会话（`workbuddy/deepseek-v4.1-flash`） | 拆分/派单/汇总/合并 |

## Codex 使用方式（本机）
- CLI：`C:\Users\Admin\AppData\Local\OpenAI\Codex\bin\<hash>\codex.exe`
- 产品设计评审：`codex exec -s read-only -C <repo> "<需求/评审提示词>"`
- 代码审核：`codex review` 或 `codex exec -s read-only "评审这次改动 …"`
- 原则：**只读优先、不让 Codex 直接改文件**；评审结论由协调会话转成修复项；Codex 不代替人签字/合并。

## 交付三段：open PR → babysit → shipping（2026-11-23 追加）

> 依据 `docs/19-pstack落地（shikar版）.md` 与 `docs/44-实施计划-pstack工程化落地.md`。
> 本节只补「从开 PR 到合并」这三段怎么走；上面的角色表不变。

**第一段 · open PR**
开发方交付 = 分支 + PR + 自测证据，**不写「已验证」结论**。PR 正文按 `.github/pull_request_template.md` 填：目标、完成条件（可判定 + 怎么验）、不做、证据（命令与实际输出摘要）。缺完成条件的 PR 不进评审队列。

**第二段 · babysit（把 PR 推到 merge-ready）**
出 PR 的人自己盯：解决冲突、等 CI 绿、逐条回应评审意见。**babysit 到 merge-ready 为止，不合并、不发布。** 分支落后 main 先 rebase 再谈结论——落后期间的改动会改变结论。

**第三段 · shipping（独立验证 → 人点头 → 合并 → 发布）**
1. **验证权独立于开发权**：由**没有参与实现的 fresh agent** 检出验证，不在开发分支上改文件：
   `git worktree add ../shikar-review-<pr> agent/<branch>`
2. 验证者拿到三样：**原始 brief、被验分支、上一轮报告**；不看开发者口头解释，对 PR 声称的每条结论**逐条复跑**。
3. 结论三态，只能选一个，不许模糊：
   - `PASS` —— 可合并
   - `PASS+NOTES` —— 可合并，附非阻断说明
   - `FAIL` —— 不可合并，列出阻断项（P0/P1 必须带复现路径，否则降级为「建议改」）
4. **合并由人点头，不自动合并。** 作者给自己签的「可合并」不算数。
5. 合并后走 `deploy/release.sh` 发布，回执与回滚见 `docs/发布与回滚.md`；发布是发布交付助手的活，开发方与审核方都不碰服务器。

**门禁口径**：本地与 CI 用同一个入口 `bash scripts/verify.sh`。CI 见 `.github/workflows/ci.yml`。
