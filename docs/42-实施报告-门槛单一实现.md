## 1. 核查结论（与报告前提不一致，必须先说清）

**main 上 `pipeline.recompute` 自 #36（`852ac47`）起已经带门槛**：

- `backend/shikar/pipeline.py` 有 `MIN_PERIODS/MIN_SPAN_DAYS/MAX_GAP_DAYS` 与 `is_sufficient()`；
- `recompute` 先判 `sufficient`，不满足写 `temperature=None, stage=None`；
- 本地复现：2 期序列（2019-02 + 2026-W46）经 `ingest` → `recompute` 后两行 temperature 均为 `None`。

线上「全员温度=50」的原因是**部署副本陈旧**（服务器停在 `1195b46`），不是 main 缺代码。Leader 已确认并完成部署，线上现在是 `origin/main` 代码、温度非空 21/19339。

## 2. 真正需要修的：门槛有两份实现

- `scripts/build_db.py` 自带 `parse_week()` + `sufficient()`；
- `backend/shikar/pipeline.py` 另有一份 `is_sufficient()`。

两份各算各的，正是「改了一条漏另一条」的结构性来源。本 PR 做去重：

- 删除 build_db 的本地 `parse_week`/`sufficient`；
- 改为 `pipeline.is_sufficient(weeks_by.get(xid, set()))`；
- 阈值仍只定义在 `pipeline`（3 / 365 / 365），数值未改。

## 4. 变异复现（更正上一版自述）

上一版写「把 build_db 改成 `min_periods=1` 后写出 2 行温度」是**错的**：单放松期数不会分叉——2 期要满足跨度 ≥365 天，缺口必然也 ≥365 天，会被 `max_gap` 拦下。

实测能分叉的形状是**只放松 `max_gap_days`**。数据取 3 期但缺口 >365 天（2019-02 / 2023-01 / 2026-W46），把 build_db 的调用改成 `max_gap_days=100000` 后：

```
after build_db: 1
after recompute(default): 0
```

判定分叉，交叉对照用例失败；还原后两条都为 0。

**独立复验（testWorker，docs/43 第二轮）：可以合并。** 全量 307；rebase 后分支含 `cefae80` + `74a2a70`（`data/fang_2026.csv` 3831 行 = W46 1955 + W48 1875），W48 数据未丢；修正后的变异形状亲验成立（3 期缺口 623 天数据 + `max_gap_days=100000` → build_db 判有温度、recompute 默认判无，分叉实锤）；W47 端到端与真实 CSV W46 对照均不回归。
