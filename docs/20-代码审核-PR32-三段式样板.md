## 必改（P0/P1）

### P1-1 并发请求下 `/api/commute` 返回 500（本次改动引入）

> **状态：已修复并复验通过 @ `e66303d`。** 独立复验（testWorker）：`263 passed`；驾车/公交各 6 并发×10 轮 = 60/60 全 200；并发期间 `/api/health` 最大 2ms。
> 改法：`create_server` 按 `PRAGMA database_list` 推导库文件路径，为 `/api/commute`
> 每请求打开独立连接（`foreign_keys=ON`、`busy_timeout=5000`），用完关闭、不持锁；
> 其余接口仍走共享连接 + `db_lock`。内存库推导不出路径，退回旧行为（仅测试）。
> 证据：新增并发用例在 `6f05f83` 上必失败（`500 != 200`），在 `e66303d` 上 6/6 通过、
> 连跑 5 轮稳定；探针 A 由 FAIL 转 PASS；全量 `263 passed`。

**位置**：`backend/shikar/api.py:550`（`do_GET` 把 `/api/commute` 移出 `db_lock`）、`backend/shikar/api.py:219`（`_handle_commute` 在锁外读写 `conn`）、`backend/shikar/commute.py:152`（`commute_for` 写缓存并 `commit`）。

**现象**：6 个并发 `/api/commute` 请求，4 个返回 500，错误为 `bad parameter or other API misuse` / `tuple index out of range`。

**证据**

```
python scripts/review/commute_probe.py --repo ../shikar-review-32
[A] 并发 6 个 /api/commute（期望 6×200）→ 2×200 / 4×500  FAIL
    500 样本: 内部错误: bad parameter or other API misuse

python scripts/review/commute_probe.py --repo <基线 main 检出>
[A] 并发 6 个 /api/commute（期望 6×200）→ 6×200 / 0×500  PASS
```

**根因**：`create_server` 传入的是**单个共享连接**（`main.py:198` `check_same_thread=False`，`api.py:596` `ThreadingHTTPServer`）。改动前所有 `conn` 访问都在 `db_lock` 内串行；改动后 `/api/commute` 整条链路（`resolve_place` 的 `place_cache` 读写、`select_commute_candidates` 的查询、`commute_cache` 写入与 `commit`）都在锁外，与其它线程共用同一连接。`resolve_place` 内部的 `commit()` 会提交另一个线程未完成的事务，`commit` 与语句执行交织即触发上述错误。

**风险**：通勤接口在正常并发下约 2/3 失败；更隐蔽的是跨请求提交彼此的事务（缓存写入不可预期）。

**建议**：先分离共享状态，再谈并发——`/api/commute` 使用**自己的连接**（每请求打开或线程本地），或把 `conn` 的所有访问重新收进 `db_lock`、只把网络请求留在锁外（读缓存 → 解锁计算 → 加锁写缓存）。前者改动小，推荐；`commute_for` 需要拆成读/写两段。

### P1-2 公交上游全部失败时仍返回 200 + 空结果

> **状态：已修复 @ `e6e0bec`。** 连续 3 条失败且零成功立即抛 `upstream|timeout`；
> 循环结束零成功同样抛错；部分失败保持 200 但带 `stats.attempted/failed` 与
> `partial=true`。证据：探针 B 由 `200/空` 变为 `502 + error`；新增两条 HTTP 用例，
> 全失败用例在 `e66303d` 上必失败（`200 != 502`）。

**位置**：`backend/shikar/commute.py:244`（`except Exception: stats["failed"] += 1; continue`）、`backend/shikar/api.py:278`。

**现象**：`mode=transit`，百度公交对每个 OD 都抛异常 → HTTP 200，`items=[]`，`stats.failed=2`，无 `error` 字段。

**证据**

```
[B] transit 上游全挂（期望 502 或明确降级）
    → status=200 items=0 stats={'total':2,'cached':0,'computed':0,'failed':2,'truncated':False} error=None
```

**根因**：P1-5 只给 `_get_json`（驾车）做了错误分类；公交路径按条吞掉所有异常，逐条失败被计成 `failed`，整体不可用与「候选都没算出来」无法区分。

**风险**：正是原审核 P1-5 要求消除的「混成成功空」；前端会把上游故障显示成「该范围没有可通勤小区」。

**建议**：区分单点失败与整体失败。全部失败（或失败率 100%）抛 `CommuteError("upstream", …, partial=stats)`；部分失败保留 200，但响应必须带 `stats.failed` 与明确的 `partial=true` 语义。百度异常也要分类（超时 / 配额 / 无路线）。

### P1-3 「按空间规则选候选」只在前 200 条里选

> **状态：已修复 @ `e6e0bec`。** 距离排序下推 SQL（`sort="distance_center"`），
> WHERE 排除无坐标，`LIMIT` 取距离 TopN，命中总数与有坐标数分别由两次查询给出。
> 证据：探针 C 返回 `Z000,Z001,Z002`（最近点），改前是 `A000,A001,A002`；
> 8000 行实测距离排序 9.5ms、整链 85.7ms（其中 72.9ms 是既有逐条补数 N+1，
> 见 P3-1，不在本提交范围）。

**位置**：`backend/shikar/catalog.py:351`（`select_commute_candidates`）、`backend/shikar/catalog.py:380`（`page_size=_MAX_PAGE_SIZE`，即 200）、`backend/shikar/catalog.py:253`（默认排序 `city, district, name, id`，与空间无关）。

**现象**：同城命中 250 个小区，真正离 A/B 中点最近的 50 个（名字排序靠后）一个都没进入候选。

**证据**

```
[E] 250 个命中，最近的 50 个名字排序在后（期望结果含 Z*）
    → total_matched=250 with_coords=200 返回含 Z*: False 前 3: ['A000','A001','A002']
```

**根因**：先用 `query_catalog(page_size=200)` 按名称序截断，再做坐标过滤与球面排序。空间规则作用在非空间序的前 200 条上，不是全量。

**风险**：北京 8000+ 小区时，「离两个上班地点都近」的排序基本失效；PR 自述「以相同过滤语义取**全部**命中」不成立。

**建议**：坐标过滤与距离排序下推到 SQL（`ORDER BY` 中点距离，`LIMIT max_candidates`），或分页拉全量再排（需给出数据量与耗时）。二者都要报告 `with_coords` / `total_matched` / `truncated` 的一致口径。

## 建议改（P2）

### P2-1 预算/429 路径从 HTTP 层不可达

**位置**：`backend/shikar/api.py:206-208`、`backend/shikar/commute.py:206,230`。

驾车候选上限 200，而预算是 8 批 × 80 = 640，永不触发；公交候选上限 40 与 `DEFAULT_MAX_TRANSIT_OD=40` 相等，`>` 条件永不成立。两条 `budget` 分支只被单测直接调用命中，生产请求走不到，429 与 partial 语义等于未验证。

**建议**：让预算与候选上限来自同一配置并保持 `候选上限 > 预算`，或在 API 层显式允许更大候选集；补一条走 HTTP 的 429 用例。

### P2-2 place_cache 实际 TTL 是 30 天，声明值未实现

**位置**：`backend/shikar/commute.py:34,36,87`。

`RESOLVE_TTL`（7 天）与 `CACHE_TTL_EMPTY`（6 小时）声明后从未被引用；`_is_fresh` 一律用 `CACHE_TTL_OK`（30 天）。证据：写入 8 天前的 `place_cache` 行，`resolve_place` 仍命中缓存，上游调用 0 次。PR 声称的「空/失败结果短 TTL 6 小时」没有对应代码——空/失败根本不写缓存行。

**建议**：`_is_fresh` 接收 ttl 参数；要么实现短 TTL，要么删掉常量并在 PR 里改正声明。

### P2-3 驾车上游中途失败：已算结果丢失、统计失真、事务悬挂

**位置**：`backend/shikar/commute.py:196-227`、`backend/shikar/api.py:277-279`。

200 个候选、第 2 批失败时：响应 502、`items=0`、`stats.computed=0`，但同一连接上 `commute_cache` 已有 80 行（未 `commit` 也未 `rollback`）。后续任一请求的 `commit()` 会把它们顺带提交；`stats` 与真实计算量不符。

**建议**：异常路径 `rollback`，并把已成功的行作为 `partial` 返回（与 budget 分支一致）；`stats.computed` 以实际写入行数为准。

### P2-4 OSM 导入在空结果时仍清空该城 OSM POI

**位置**：`scripts/osm_poi.py:155`（无条件 `DELETE ... id LIKE 'osm:%' AND city=?`）。

`pois` 为空（pbf 传错城市、解析失败、过滤后为空）时，先删该城全部 OSM POI，再插入 0 条。与 `docs/14` 的 P2-15（空结果删站）同类问题，本次未加守卫。

**建议**：`if not pois: 中止并回滚`，或要求 `--allow-empty` 显式确认。

### P2-5 百度 POI 删除用子串包含匹配

**位置**：`scripts/osm_poi.py:165-178`。

`bn == onm or bn in onm or onm in bn` 会把「北京南站南广场」与「北京南站」、「北京实验小学分校」与「北京实验小学」判为同一设施并删除百度侧记录；同时是 `O(百度 × OSM)` 的全量比较，北京量级下为百万次字符串操作，脚本耗时随数据量平方增长。

**建议**：同名优先 + 距离阈值（如 300m）作为「确认对应」的联合条件；按 `(type, 名称前 4 字)` 建索引降复杂度，并给出实测耗时。

### P2-6 缓存时间解析依赖本机时区

**位置**：`backend/shikar/commute.py:87-96`。

`time.mktime(strptime(...)) - time.timezone` 依赖本机时区与「无夏令时」假设；在有 DST 的机器上偏差 1 小时，跨时区部署时 TTL 判定整体漂移。

**建议**：`datetime.strptime(...).replace(tzinfo=timezone.utc).timestamp()`，或直接存 epoch 整数。

### P2-7 分支落后 origin/main 且 api.py 有冲突（已处理，待重验）

**位置**：`backend/shikar/api.py`。

初审时分支落后 `origin/main` 17 个提交（merge base `ddc7660`），其中 `b5e2d3c`、`1195b46` 直接改了通勤与 `/api/suggest`。实测 `git merge origin/main` → `CONFLICT (content): Merge conflict in backend/shikar/api.py`。

**处理结果**（`6f05f83`）：已 rebase 到 `origin/main` 并解决冲突——保留 `origin/main` 的坐标直传（`latA/lngA/latB/lngB`、`cityA/cityB`、`_place()`）并接入新签名 `resolve_place(conn, text, city)`；`test_suggest_and_coords.py` 适配 `commute_for` 的三元返回与 `select_commute_candidates`。

**复验**：`261 passed`；探针 A–E 结论与初审一致（并发 5/6 失败、transit 仍 200 空、候选仍只在前 200 条内排序）。冲突解决不改变任何 P1 结论；P1-1 随后由 `e66303d` 单独修复。
