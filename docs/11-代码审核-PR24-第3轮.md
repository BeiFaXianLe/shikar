## 三、新增 / 遗留问题

### 【P1｜阻断】价格期次 + 地铁筛选参数绑定顺序错位 → 有总数无列表
- 位置：`backend/shikar/catalog.py:229-235`，`query_catalog` 分页 SQL。
- 问题：分页 SQL 中距离子查询 `distance_sql` 位于 `SELECT` 子句（文本最前，`catalog.py:232`），其占位符早于 `from_sql` 的期次占位符 `m.week=?`（`catalog.py:163-170`）；但参数按 `metric_join_params + distance_params + params + [size_n, offset]` 传入（`catalog.py:234`），顺序与 SQL 文本相反。结果 `line_id IN ('2026-W46')`、`m.week='a'` 整体错位。`total` 走 COUNT 查询（无 `distance_sql`），故总数正确、列表为空。
- 复现（协调方独立执行 `query_catalog`，同内存夹具）：

  | 查询条件 | total | items |
  |---|---:|---|
  | `line=a&subway_max=0.5`（无期次） | 2 | `['x1','x2']` ✅ |
  | `+ price_week=2026-W46` | 2 | `[]` ❌ |
  | `price_week=2026-W46&station=s1&subway_max=0.5` | 1 | `[]` ❌ |
  | `price_week=2026-W46&subway_max=0.5`（无线路/站点） | 2 | `['x1','x2']` ✅ |

  即：只要**同时**给了 `price_week` 与 `line`/`station`（距离子查询含占位符）就触发；不加 `sort=subway_distance` 同样触发。上一版 `22c5139` 在该夹具返回正确结果，**确认为本轮新引入回归**。
- 风险：期次 + 地铁（核心筛选组合）静默返回空列表，用户以为无结果；现有测试未覆盖该组合，故未检出。
- 建议：分页参数按 SQL 出现顺序绑定，改为 `distance_params + metric_join_params + params + [size_n, offset]`；并补「期次 + 线路」「期次 + 单站」组合回归测试。

### 【P2】价格「来源」未落地
- 位置：`backend/shikar/catalog.py:270`、`web/app.js:995-1001`。
- 问题：`price_source_week` 仅重复期次，并非数据来源（链家 2019-02 / 房天下 2026-W46）；前端「价源：YYYY」实为期次。
- 建议：按周次映射真实来源并返回/展示（可用 `source_snapshot` 或 week→平台规则）。

### 【P3｜观察】删除 `--require-subway` 参数
- 位置：`backend/shikar/main.py:183-187`。
- 说明：以 `--allow-no-subway` 取代旧 `--require-subway`；实测旧参数现报 `unrecognized arguments` 退出 2。仓库内已无任何对 `--require-subway` 的引用，且该参数为同 PR 上一迭代（22c5139）新增、尚未合并发布，故不构成对外兼容破坏，仅提示注意。
