# 57 · 流程门禁：PR 正文审核三段式 + 独立验证三态（上线与回退）

依据：2026-11-23 复盘（8 个 PR 里 7 个在无审核、无独立验证下合并上线，PR 正文那两栏全空，CI 绿被当成验证结论）。
要拦的只有一件事：**栏位空着也能合并**。

## 一、它做什么

`scripts/check_pr_review.sh` 读 PR 正文（不是代码），校验两项：

1. **「审核（三段式）」三张表都填了实质内容** —— 必改（P0/P1）、建议改（P2）、可接受风险（P3 或明示豁免）。
   只有表头、空单元格、`<待填>` `—` `…` 这类占位符都算没填；确实没有问题要写「无」，不能留空。
2. **「独立验证」**：验证者字段非空、且**不是 PR 作者本人**（作者自己签不算）；`PASS` / `PASS+NOTES` / `FAIL` **恰好勾一个**，
   并且**必须是通过类结论**——勾 `FAIL` 即判不通过（验证说不可合并，就不许合并），并把「阻断项」一并打印出来。

   「是不是同一个人」做过**身份归一**：去掉括号及其内容、去掉空白（含全角空格）、小写，取核心名再比；
   且拒收**以作者名开头**的验证者。所以 `宝拉（代签）`、`宝拉代签`、`宝拉 （代签）` 都会被拦；
   而 `代码审核智能体` 与作者 `宝拉` 无关，正常放行。

任一不满足：退出码 1，逐条打印缺哪一项。退出码 2 是用法/读取错误，CI 里同样是红。

字段口径完全按 `.github/pull_request_template.md` 现有结构解析，没有另造字段：改模板的标题（`## 审核`、`## 独立验证`、`### 必改` 等关键字）会直接让门禁失效。

## 二、它挂在哪

- `.github/workflows/ci.yml` 的 job **`pr-review-gate`**，`name: 流程门禁`。
  **这个 name 就是分支保护引用的 check 名，改了等于把门禁摘掉。**
- 触发：`pull_request` 的 `opened / synchronize / reopened / edited`。
  `edited` 是必需的——不然审完之后把结论填进正文，检查不会重跑，永远红，只能靠空提交解堵。
- 正文取事件负载（`github.event.pull_request.body`），不调 GitHub API：少一次网络依赖，也不用额外 token 权限。

## 三、怎么用

```bash
# 查真实 PR（本地，需要 gh 已登录）
bash scripts/check_pr_review.sh --pr 47

# 自测/离线核对
bash scripts/check_pr_review.sh --body-file body.md --author BeiFaXianLe
```

## 四、分支保护（main）

`required_status_checks.contexts` 在原两项之外增加 `流程门禁`：

- `verify（pytest + 静态门禁）`
- `shellcheck（发布脚本）`
- `流程门禁` ← 新增

`strict=true`、`enforce_admins`、`allow_force_pushes`、`allow_deletions`、`required_conversation_resolution` 均保持改前取值。

改前快照：`.github/branch-protection-main-20261123-before.json`。

### 只加一项 context（不动其它设置）

```bash
gh api -X POST repos/BeiFaXianLe/shikar/branches/main/protection/required_status_checks/contexts \
  -f 'contexts[]=流程门禁'
gh api repos/BeiFaXianLe/shikar/branches/main/protection \
  --jq '.required_status_checks.contexts'
```

### 回退

```bash
# 回退到改前状态（两项 check，其余设置一并不变）
gh api -X PUT repos/BeiFaXianLe/shikar/branches/main/protection \
  --input .github/branch-protection-main-20261123-before.json
```

> 注意：改分支保护是**不可逆动作**的邻居——加了就挡住所有 PR 的合并。加之前必须确认
> `流程门禁` 这个 check 真的会在 PR 上出现、且名字一模一样（在某个真实 PR 的 checks 里看得到），
> 否则该 check 永不出现，所有 PR 永久无法合并，比门禁失效更糟。

## 五、已知取舍
- 改 PR 正文会重跑整个 CI（`concurrency` 会取消进行中的旧运行）。换来的是「填完即变绿」，不需要空提交。
- 脚本只判「填了没有」，不判「填得对不对」。判内容质量仍是审核方的活；
  这条门禁挡的是「跳过流程」，不是替代审核。
- 写「无」可以过必改表——这是有意的：审查后确实没有 P0/P1 时，必须显式写「无」，而不是留空。
- 「同一个人的判定」只看正文里的名字：脚本看不到背后是谁，挡不住「同一个人既写代码、又把验证者写成另一个名字」。
  这一层靠人点头与流程纪律，不是脚本能解的。
- 门禁自检依赖 `scripts/fixtures/` 四份固定样本（填齐 / 缺栏位 / 三态勾 FAIL / 验证者带后缀）。
  改这几份样本等于改门禁的「标准答案」，谁改谁必须同时确认自检仍能拦住违规形态。
- **回退是整体覆盖**：`--input <快照>` 的 `PUT` 会把 protection 整体写回快照里的值，
  若在那之后别人改过保护设置（例如新增 required check），回退会一并抹掉。回退前先
  `gh api repos/BeiFaXianLe/shikar/branches/main/protection` 读当前值对比，再决定是否逐项改回去。
