## 3. 结论（按 P0–P3 分级）

### P0-1 · 温度公式 75% 的权重永久是中性值，任何温度都只能是 50

**等级**：P0
**位置**：`backend/shikar/scoring.py:81-82`（权重）+ `backend/shikar/pipeline.py:295-300`（分项来源）
**问题**：温度 = `0.40*n(mom4) + 0.25*n(absorb) + 0.20*(100-n(bargain)) + 0.15*n(heat)`。全库 `absorb`/`bargain`/`heat` 非空行数为 **0**，`percentile_normalize` 在样本不足时返回中性 50。于是：

```
temperature = 0.40*n(mom4) + 0.25*50 + 0.20*(100-50) + 0.15*50
            = 0.40*n(mom4) + 37.5
```

即使 `n(mom4)` 取极值 0 或 100，温度也只能落在 **[37.5, 77.5]**，且绝大多数时候 `n(mom4)` 本身也是 50（样本 <4），结果恒为 **50.0**。

**证据**：
- `SELECT COUNT(absorb), COUNT(bargain), COUNT(heat), COUNT(vol30) FROM xiaoqu_metric_weekly` → `(0,0,0,0)`
- `SELECT temperature, COUNT(*) FROM xiaoqu_metric_weekly WHERE temperature IS NOT NULL GROUP BY temperature` → `(50.0, 27)`
- 恒等式验算：`0.40*50 + 0.25*50 + 0.20*(100-50) + 0.15*50 = 50.0` ✓
- 27 行里 26 行 `stage='温和'`（唯一例外是 mom4<0 的那行判「下行」）

**已证实**。

**风险**：这是**产品可用性问题**，不是数据量问题。即使把期次补到 100 期，只要 vol30/bargain/heat 仍然为空，温度依然恒为 50。当前的「数据不足」空态是诚实的，但一旦有小区过门槛，展示的 50.0 就是**编造的中性值**——比空态更误导。

**修复路径**：
1. **口径层（推荐，不需新数据）**：三分项缺失时不应回退中性 50，而应「按可用分项重新归一化权重」。即 `temperature = Σ(w_i * n_i) / Σ(w_i)`，只对非空分项求和。这样只有 mom4 时温度 = `n(mom4)`，至少有 0–100 的真实分布。
2. **数据层（成本高）**：补 `vol30`（近 30 天成交量）、`bargain`（议价空间）、`heat`（关注热度）。当前数据源（房天下公开聚合页）不提供这三项，需换源或加采集，受限流影响。
3. **文档层**：`docs/04 §1.1` 已注明三项基本为空，但未说明「因此温度恒为 50」，需补一句显式结论。

**是否需改数据**：方案 1 不改数据，只改代码口径。方案 2 需新增采集。
**是否需人确认**：**是**（涉及产品口径定义）。

### P0-2 · `mom4` 口径错误：262 行里 0 行是真正的「4 周动量」

**等级**：P0
**位置**：`backend/shikar/pipeline.py:305-306`
**问题**：
```python
if i >= 4 and prices[i] is not None and prices[i - 4] not in (None, 0.0):
    mom4s.append(prices[i] / prices[i - 4] - 1.0)
```
取的是「该小区序列里前第 4 **条记录**」，不是「4 **周**前」。当序列稀疏（月粒度与周粒度混采、或中间跨 2019 年）时，前第 4 条可能相隔数月甚至数年。

**证据**（逐行还原每行 mom4 的基准期跨度）：

| 跨度区间 | 行数 |
|---|---|
| ≤35 天（≈4 周，口径正确） | **0** |
| 36–120 天 | 1 |
| 121–400 天 | 91 |
| >400 天（跨 2019 / 跨月） | 170 |

最极端样例：
```
天津|1110833297  2026-W48 vs 2019-02   20043 → 12222   mom4 = -0.3902   跨度 2852 天
天津|1110740115  2026-W48 vs 2019-02   11400 → 4902    mom4 = -0.5700   跨度 2852 天
```

**前端把它标成「近月环比」**（`web/app.js:1100`：`"近月 " + fmtSigned(latest_mom*100) + "%"`；`:1715`：`readoutItem("近月环比", mom)`）。实际含义是「相对序列前第 4 条记录的变化」，跨度可达 7.8 年。**已证实**。

**风险**：
- 「升温最快 / 降温最快」两榜完全建立在错误的 mom4 上。天津榜首 `mom4=0.6192` 实际是某个月对某个更早月份的涨跌，不是近期动量。
- 详情页「近月环比」数字对用户是**错误陈述**。
- 正确口径下（跨度 ≤35 天）可用行数为 **0**——意味着修好口径后，mom4 暂时**全部为空**，榜单会更空。这是诚实的代价。

**修复路径**：
1. 改为按**日历差**匹配：`mom4 = price(t) / price(t - 28天) - 1`，找不到落在 28±7 天窗口内的期次则置 `None`。
2. 前端文案随之改为「较 N 天前」，或数据不足时不显示。
3. 补一条测试用例：构造「2019-02 + 2026-W48」两期小区，断言 `mom4 IS NULL`。

**是否需改数据**：是（需重跑 `recompute_metrics.py` 重算 mom4，只改派生列，不动原始价）。
**是否需人确认**：**是**。

**问题**：因为所有合格小区温度都是 50.0，`top_hot`（降序）与 `top_cold`（升序）取到的是**同一批小区**。`top_rising` 与 `top_falling` 同理（都基于 `mom4`，且样本极小）。

|---|---|---|---|---|---|---|
| 北京 | 长安悦玺、龙城花园五期、永安西里(房山)、西关北路小区（全 50.0） | 同左 | **是** | 长安悦玺 +1.51%、龙城花园五期 -7.65% | 同左（顺序反） | **是** |

**是否需改数据**：否。
**是否需人确认**：建议确认（涉及接口字段新增）。

### P3-2 · 备份脚本的「缺失即跳过」会静默产出不完整备份

**等级**：P3
**位置**：`scripts/backup_critical.py:126-131`
**问题**：
```python
if not os.path.exists(full):
```

```
09:59 备份: files/fang_preview_all.csv, files/fang_2026.csv, history2019.csv, db.sql
```

`SNAPSHOT_LOG.md` 记录该 CSV「此前缺失，已从 `critical-20261123_045022.tar.gz` 取回」——说明它曾真的丢过一轮。

**已证实**。

**风险**：中低。当前 09:59 那份是完整的（三个 CSV 哈希与本地逐一核对一致），但机制上「不可再生数据缺失」不会阻止备份完成与推送，会在最需要它的时候给出虚假安全感。

**是否需改数据**：否。
