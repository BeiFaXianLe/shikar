# shikar · 功能扩展：地铁 / 学区 / 医院 / 高铁 / 通勤 —— 可行性与技术选型评估

> 版本 v0.1（2026-11-09）｜配套原型：`prototype/index.html`（可交互，模拟数据）
> 结论先行：**三项都可实现**；1（地铁沿线）与 2（学校/医院/高铁 POI + 排名）**免费数据可做、成本低**；3（双点加权通勤）**依赖商业路径规划 API，成本/配额是主要约束**。整体建议分三期落地。

---

## 0. 一句话结论

- **可实现性：高**（技术无硬门槛，难点在**POI/路径数据的获取与配额**，不在开发）。
- **市场：确实少见「地铁沿线 + 学区/医疗/高铁 Top20 + 双点加权通勤」合一的个人看板**；贝壳/高德/学区房平台各自只有其中一块，没有整合成这种“按条件找小区”的决策工具 —— **这是差异化机会**。
- **技术选型建议**：个人本地继续用 **SQLite** + **Python 离线预计算 + 物化宽表**；不要一上来上 PostGIS。等要多城市/实时空间查询再迁移 **PostgreSQL + PostGIS**。
- **主要风险**：POI 与路径 API 的 **ToS / 配额 / 费用**；通勤全量计算成本高，需“先粗筛再精算”。

---

## 1. 功能一：地铁沿线找小区

**要什么**：给定城市/线路/站点，找出「沿某地铁线」或「距某站 ≤R」的小区。

**数据**
- 地铁**线路走向（polyline）与站点坐标**：可用公开 GeoJSON（高德/OSM/GitHub 城市轨道数据），**免费**；或高德 POI「地铁站」接口（需 key，有免费额度）。
- 小区经纬度：**我们已有的 2019 链家数据集就带 `longitude/latitude`（16,622 条）**，可直接复用。

**算法**
- 「距某站 ≤ R」：Haversine 球面距离，简单。
- 「沿线」：小区到线路 polyline 的**点到折线最短距离** ≤ R（纯 Python 可实现，或用 shapely）。
- 预计算成 `community_subway(community_id, line, station, distance_km)`，加索引即可秒查。

**结论**：**可行，成本最低**。先做这个最稳。

## 2. 功能二：学校 / 医院 / 高铁站 POI + 排名 + 宽表

**要什么**
- 记录小区周边的**学校（小学/初中/高中）、医院、高铁站**；
- 支持自定义筛选；能看「某医院/学校周边小区排名 Top 20」；
- 学校、医院各做一个明细菜单，但首页也能筛选。

**数据来源（候选）**
| 来源 | 覆盖 | 成本 | 备注 |
|---|---|---|---|
| 高德 POI 搜索 API（分类码：学校 1412xx / 医院 0901xx / 火车站 1505xx） | 好 | 免费额度 + 超量按量 | 需申请 key；ToS 允许展示需遵守 |
| 百度地图 POI API | 好 | 同上 | 备选 |
| OpenStreetMap Overpass | 中（学校/医院一般，高铁站少） | 免费 | 无配额但质量参差 |
> 学校“等级/重点”通常不在 POI 里，需要一份**重点校名单**（人工/公开名单）来打分；否则只能按“距离/类型”排。

**存储方案：宽表 vs 规范化（重点评估）**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **纯宽表** `community_features(community_id, nearest_subway_line/dist, primary_cnt, primary_min_dist, middle_* , high_*, hospital_cnt, hospital_min_dist, hsr_dist, ...)` | 首页筛选**一条 SQL 秒出**、实现简单 | 维度一多列爆炸；新增维度要改表；明细/排名不好表达 | **用作“物化宽表”**（ETL 生成），不手写维护 |
| **纯规范化** `poi(id,type,name,grade,lat,lng)` + `community_poi(community_id,poi_id,type,distance_km)` | 灵活、可做任意排名/明细 | 首页多条件筛选需多表 join，慢 | **用作明细/排名底座** |
| **推荐：规范化明细 + 物化宽表（混合）** | 明细灵活 + 首页快 | 需 ETL 同步 | ✅ 采用 |

**排名 Top20 的做法**：`community_poi` 按 `(poi_id, distance_km)` 建索引；某医院/学校 → `ORDER BY distance_km LIMIT 20`。可在 ETL 时为每个 POI 预生成 top20 快照。

**计算量**：17,439 小区 × 每类 POI（假设单城 3–5 千）= 上亿对距离。**必须用网格/经纬度矩形预筛**（只在 ~5km 邻域内算精确距离），并限定每类 POI 半径与数量；否则会爆。

**技术选型**：个人量级 **SQLite + Python 离线 ETL + 预计算宽表** 足够；**无需 PostGIS**。若扩到多城市/城市级全量且要“任意半径即时查”，再上 **PostgreSQL + PostGIS**（`ST_DWithin` 建 GiST 索引）。

**结论**：**可行**；工作量中等（数据采集 + 距离预计算 + 宽表 + 两个明细页）。合规上注意 POI API 的展示条款与配额。

## 3. 功能三：双点通勤加权

**要什么**：录两个地点 A/B，设权重（A 优先 / 均衡 / B 优先），按通勤时间排小区。

**关键依赖：路径规划 / 时间矩阵 API**
| 方案 | 驾车 | 公交/地铁 | 成本 | 说明 |
|---|---|---|---|---|
| 高德「路径规划/时间矩阵」API | ✅ | ✅（公交方案） | 有免费额度，超量按量计费 | 公交最贴合“通勤”，首选 |
| 百度地图 路线 API | ✅ | ✅ | 同上 | 备选 |
| 自建 OSRM / Valhalla | ✅ | ❌（无实时公交） | 服务器成本 | 只适合驾车近似 |

**算法**：对候选小区 c：`tA(c)`、`tB(c)`；
- 加权分：`score = w·tA + (1−w)·tB`（w=0.5 均衡）；
- 均衡另一种定义可用 `max(tA,tB)` 或几何均值，避免“一个极近、一个极远”被平均掩盖。
**成本控制**：全量 17k×2 次调用太贵——**先用前两类条件（地铁/学区/预算）粗筛到几百个候选，再对候选算通勤**；并把 OD 结果**本地缓存**（SQLite，带 TTL），重复查询不重复计费。

**结论**：**可实现，但要花钱/配额**；建议作为「精算步骤」，不做全量实时。

## 4. 技术选型总结（当前项目）

| 维度 | 建议 | 理由 |
|---|---|---|
| 数据库 | **继续 SQLite**；新增 `poi`、`community_poi` 明细 + `community_features` 物化宽表 | 个人本地、零运维、读快 |
| 空间计算 | **Python 离线预计算**（网格预筛 + Haversine + 点到折线） | 零依赖、可重跑 |
| 何时上 PostGIS | 多城市全量 + 任意半径即时查询 + 并发 | 那时 SQLite 空间能力不足 |
| 数据管道 | 脚本：拉 POI → 落库 → 算距离 → 生成宽表 → 重建 `data/shikar.db` | 与现有 `build_db.py` 一脉相承，可每周随快照刷新 |
| 前端 | 首页加“高级筛选” + 学校/医院明细页 + 通勤页（原型已出） | 复用现有“年鉴”视觉 |

## 5. 分期建议与工作量（粗估）

| 期 | 内容 | 依赖 | 工作量 |
|---|---|---|---|
| P1 | 地铁沿线（线路/站点/距离/沿线筛选） | 公开 GeoJSON + 已有经纬度 | 小（3–5 人天） |
| P2 | 学校/医院/高铁 POI + 明细菜单 + Top20 + 宽表 | 高德/百度 POI key | 中（5–8 人天，含数据采集） |
| P3 | 双点加权通勤 | 路径规划 API（付费/配额） | 中（5–8 人天，含缓存与成本控制） |

---

## 6. 风险与合规
- **P0 POI/路径 API ToS 与配额**：需申请 key、遵守展示条款；超量计费。
- **P1 数据质量**：学校“好坏/重点”POI 不体现，需外部名单；否则排名只按距离，易被误解。
- **P1 通勤成本**：全量实时不可行，必须粗筛+缓存+抽样。
- **P2 口径一致性**：POI 距离是直线距离，不等于步行/驾车距离；文案要标明。

---

## 7. 市场判断
- 贝壳/安居客：**地图找房 + 地铁/学区标签**，但不做“医院/学校/高铁 Top20 小区排名”，也不做“双点加权通勤”。
- 高德/百度：**通勤时间**强，但不是“小区行情 + 学区医疗”的决策工具。
- 学区房类平台：只有学校，没有行情/通勤/医疗整合。
- **把五件事合成一个「按条件找小区」的个人看板，市面上确实少见**——差异化成立，值得做。

---

## 8. 结论
- **可以实现**：功能一、二免费可落；功能三需商业 API（有成本）。
- 推荐节奏：**先 P1 地铁沿线（零成本、见效快）→ P2 学校/医院/高铁 → P3 通勤**。
- 技术选型：**SQLite + 离线预计算 + 物化宽表**，够用且与现有架构一致；规模上来再迁 PostGIS。
