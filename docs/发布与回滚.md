# 发布与回滚（shikar）

> 依据：`docs/19-pstack落地（shikar版）.md` 规则一/三；`docs/44-实施计划-pstack工程化落地.md`。
> 本文所有服务器事实均为 **2026-11-23 实测**（命令与输出见各节「证据」），不是推测。
> 一句话：**合并后由发布交付助手执行 `deploy/release.sh`；发布失败自动回滚；不可逆动作必须人先点头。**

## 1. 服务器事实（实测）

| 项 | 值 | 证据 |
|---|---|---|
| 主机 | `192.144.183.46` | — |
| 登录 | `ssh -i ~/.ssh/dsh_ed25519 ubuntu@192.144.183.46`（免密，`sudo -n` 可用） | `sudo -n true` → OK |
| 部署路径 | `/opt/shikar`（git clone，属主 ubuntu） | `ls -la /opt/` |
| 服务 | systemd 单元 `shikar.service`，`active`/`enabled`，`User=ubuntu` | `systemctl cat shikar` |
| 工作目录 | `/opt/shikar/backend` | 同上 `WorkingDirectory` |
| 启动命令 | `/usr/bin/python3 -m shikar.main --db /opt/shikar/data/shikar.db --host 0.0.0.0 --port 8080 --web-root /opt/shikar/web` | 同上 `ExecStart` |
| 监听端口 | `8080`（`0.0.0.0`），**直接对外**：`http://192.144.183.46:8080` | 本机 `curl 127.0.0.1:8080/api/health` → `{"status": "ok"}`；外网 `curl 192.144.183.46:8080/` → 200 |
| nginx | **没有反代到 8080**。80 端口属同机另一站（`vidlearn`，`default_server`），访问 `/` 会 302 到它的 `/login` | `grep -rn 8080 /etc/nginx/sites-enabled/` → 无结果 |
| Python | `3.14.4`（**无第三方运行时依赖**，纯标准库） | `python3 -V` |
| 数据库 | `/opt/shikar/data/shikar.db`，约 **259 MB** | `ls -lh data/` |
| 磁盘 | 根分区 39G，已用 29G，**可用 ~8.9G（77%）** | `df -h /` |

### 1.1 已知问题：服务器 git 元数据是脏的（**重要**）

`git -C /opt/shikar status` 显示 23 个文件被修改、6501 行增删，`HEAD` 停在 `1195b46`。

**实测结论：文件内容是当前 main，只是 git 没跟着更新。**

逐一比对 9 个关键文件的 blob 哈希（把服务器文件按 LF 归一后计算），与本地 `main` 的全部一致：

```
backend/shikar/api.py       10c57b0…  ==  10c57b0…
backend/shikar/commute.py   8d0897d…  ==  8d0897d…
backend/shikar/pipeline.py  b59c296…  ==  b59c296…
backend/shikar/catalog.py   18d3161…  ==  18d3161…
backend/shikar/overview.py  ebbf89a…  ==  ebbf89a…
backend/shikar/storage.py   64a9672…  ==  64a9672…
backend/shikar/main.py      47952db…  ==  47952db…
web/app.js / index.html / styles.css、scripts/build_db.py、backend/pytest.ini 同样一致
data/fang_2026.csv          be2b91f…  ==  be2b91f…
```

原因：历史上用「拷文件」上线，文件换了但没提交，所以 git 以为自己在旧版本。
**影响**：`git pull` / `git reset --hard` 这类操作会把「其实正确的内容」当成脏改动处理，甚至可能覆盖 `data/` 下的周更数据。所以发布脚本**不依赖工作区**，只用 `git archive <commit>` 取代码 + rsync 覆盖代码目录。

> 待办（P2）：择机在服务器上把 git 元数据归位（`git fetch && git reset --hard origin/main`），
> 或干脆不再要求 `/opt/shikar` 是 git 仓库。**动它之前要先确认 `data/` 不被牵连**，属人的决定。

## 2. 谁能发布

| 角色 | 能做什么 |
|---|---|
| **发布交付助手** | PR 已合并 + CI green + 人已确认 → 执行 `deploy/release.sh`，出部署回执 |
| 宝拉 | 一切；不可逆动作的唯一确认人 |
| 开发智能体 | **不发布**。只写代码、开 PR |
| 代码审核智能体 | **不发布、不合并**。做独立验证，给 PASS / PASS+NOTES / FAIL |
| 数据维护（`deploy/refresh.sh`） | 每周抓数 + 重建库，与本脚本是两条线，见 §6 |
| 自动对齐（`shikar-release.timer`） | 每天 05:20 把**已合并的** `origin/main` 搬到服务器：不合并、不改配置、不动 `data/`；失败自动回滚。见 §3.1 |

## 3. 正常发布

```bash
ssh -i ~/.ssh/dsh_ed25519 ubuntu@192.144.183.46
cd /opt/shikar

# 1) 先看会做什么（不改任何文件）
bash deploy/release.sh --dry-run

# 2) 正式发布远端 main
bash deploy/release.sh

# 发布指定 tag 或提交
bash deploy/release.sh --ref v2026.11.23
bash deploy/release.sh --ref 50caf67

# 无人值守（CI / 助手调用；跳过交互确认）
bash deploy/release.sh --yes
```

脚本按顺序做这些事（每步失败即停并回滚）：

1. **前置检查**：`/opt/shikar` 存在且是 git 仓库；`git/tar/rsync/curl` 齐备。
2. **解析目标**：`git fetch` 后优先取 `origin/<ref>`（服务器本地分支不可信，见 §1.1）。
3. **幂等判断**：`.deployed-release` 里记录的提交与目标相同 → 不搬文件，只做健康检查；不健康就重启一次。
4. **备份**：把将要被覆盖的 `backend web scripts deploy` 打包到 `.releases/<ID>/code.tar.gz`。**不含 `data/`、不含 `.secrets/`**。
5. **同步**：`git archive <commit>` 导出到临时目录，再 `rsync -a --delete` 覆盖四个代码目录（排除 `__pycache__`）。
   只同步 `backend web scripts deploy`；`.github/`、`docs/`、`data/`、`.secrets/` **不会**上服务器（生产不需要前两者，后两者是不能碰）。
6. **服务端测试**：`cd /opt/shikar/backend && pytest`。未装 `pyosmium` 时显式跳过 `tests/test_osm_poi.py`（打印告警，不静默）。
7. **重启**：`sudo -n systemctl restart shikar`。
8. **健康检查**：轮询 `http://127.0.0.1:8080/api/health` 直到 `{"status": "ok"}`（最多 40s）。
9. **冒烟**：`/api/overview` 必须有 `week` 且有城市数据（只断言结构，不断言数值——数值依赖数据，不该卡发布）。
10. **回执**：写 `.deployed-release`，追加一行到 `.releases/history.log`。

## 3.1 每日自动对齐（`shikar-release.timer`，每天 05:20）

人不用每天手动发布：`shikar-release.timer` 每天 05:20 拉起 `shikar-release.service`，把 `/opt/shikar` 对齐到 **`origin/main`**。

触发链：

1. `ExecStartPre`：`git -C /opt/shikar fetch --prune origin` —— **拉不到远端就整单失败、不发旧版**（`release.sh` 自己 fetch 失败会退回本地引用，那会「报成功但没对齐」，无人值守不接受）。
2. `ExecCondition`：`shikar-refresh.service` 正在跑（active/activating/reloading/deactivating）就**跳过今天这次**，systemd 记为 `condition failed`（不算失败）。原因：两条线都重启 `shikar`，且 `rsync --delete deploy/` 会替换正在执行的 `refresh.sh`。
3. `ExecStart`：`deploy/release.sh --yes` —— 复用 §3 的完整流程（幂等、发布点备份、服务端 pytest、健康检查、冒烟、失败自动回滚），**只同步 `backend web scripts deploy`，不碰 `data/` 与 `.secrets/`**。

**它只搬运、不决策**：不合并 PR、不改配置、不改仓库保护设置；「合并由人点头」不变。没有新提交时幂等跳过（不搬文件、不重启，只做健康检查）。

怎么确认今天对不对齐：

```bash
git -C /opt/shikar rev-parse --short origin/main    # 目标
grep COMMIT /opt/shikar/.deployed-release           # 已部署（相同即对齐）
journalctl -u shikar-release -n 60 --no-pager       # 失败/跳过原因
tail -3 /opt/shikar/.releases/history.log           # 每次真正发布追加一行
```

紧急处置：立刻对齐 `sudo systemctl start shikar-release.service`；压住不动 `sudo systemctl disable --now shikar-release.timer`；回滚仍是 `bash deploy/release.sh --rollback latest`（人决定）。

安装/卸载/排查细节见 [`docs/48-定时任务运维手册（抓数每周+版本对齐每日）.md`](48-定时任务运维手册（抓数每周+版本对齐每日）.md)。

## 4. 回滚

```bash
bash deploy/release.sh --list                 # 看有哪些发布点
bash deploy/release.sh --rollback latest      # 回到上一个发布点
bash deploy/release.sh --rollback 20261123-132202
```

回滚做三件事：还原 `code.tar.gz` → 重启 → 健康检查。**只回代码，不动 `data/`**。

自动回滚：发布过程中同步失败 / 测试失败 / 重启失败 / 健康检查或冒烟失败，脚本都会自动回滚到发布前代码并以非 0 退出，同时把发布包留在 `.releases/<ID>/` 供排查。

### 手工兜底（脚本本身坏了的时候）

```bash
cd /opt/shikar
ls .releases/                                   # 找最近一个发布点
tar -xzf .releases/<ID>/code.tar.gz -C /opt/shikar
sudo -n systemctl restart shikar
curl -s http://127.0.0.1:8080/api/health        # 期望 {"status": "ok"}
journalctl -u shikar -n 100 --no-pager          # 起不来时看这里
```

## 5. 不可逆动作（必须先经人确认）

以下动作**不要**由助手自行执行，先问宝拉：

| 动作 | 为什么不可逆 |
|---|---|
| `scripts/build_db.py`（重建库） | 原子替换 `data/shikar.db`（259MB），失败即整站无数据；旧库只剩 `.prev` 一份 |
| `deploy/refresh.sh`（每周抓数） | 会向 `data/fang_preview_all.csv` 追加历史成交，**丢一次就永久缺失** |
| 删除 `.releases/` 旧发布点 | 删掉就没有回滚点了；磁盘只剩 ~8.9G，删之前先看 `df -h` |
| 改 nginx 站点 / 证书 | 影响同机其它站点（`vidlearn` 占着 80 默认站） |
| 升级系统包 / Python | 可能连带 `pyosmium`、systemd 单元行为变化 |
| `git reset --hard` / 清理服务器仓库 | 见 §1.1，有覆盖 `data/` 的风险 |

脚本对第 3 项只提醒不自动删：发布点超过 `KEEP_RELEASES`（默认 5）时打印告警和剩余磁盘，不删。

## 6. 与数据维护（`deploy/refresh.sh`）的边界

| | `deploy/release.sh` | `deploy/refresh.sh` |
|---|---|---|
| 触发 | PR 合并后，按发布单执行 | 每周定时 |
| 改什么 | 只改代码（`backend web scripts deploy`） | 抓数 + 重建库 + 重算指标 + 重启 |
| 碰 `data/` | **不碰** | 大量写入 |
| 失败后果 | 自动回滚代码，服务仍在旧版本 | 库不替换，保留旧库；不重启 |

两条线都会重启 `shikar`，**不要同时跑**。若同一时段都要动，先跑 release 再跑 refresh。

三条补充（2026-11-23）：

1. 定时任务单元（抓数每周一 04:30 / 版本对齐每天 05:20）的安装、查看、失败判定、停用，见 [`docs/48`](48-定时任务运维手册（抓数每周+版本对齐每日）.md)；单元源文件是 `deploy/systemd/*`，用 `deploy/install-timers.sh` 装/卸/查。
2. **抓数运行中不要发布**：`rsync -a --delete deploy/` 会替换正在执行的 `refresh.sh`（bash 边读边执行）。手动发布前先 `systemctl is-active shikar-refresh.service`（期望 `inactive`）；每日自动对齐已由 `shikar-release.service` 的 `ExecCondition` 自动兜住。
3. 事实来源：抓数流程 = `deploy/refresh.sh`（服务器 md5 与仓库 main 一致）；发布流程 = `deploy/release.sh`；单元 = `deploy/systemd/*`。服务器 `/etc/systemd/system/shikar-*` 与 `.deployed-release` 是部署产物，不手改。

## 7. 发布回执（发布交付助手的输出格式）

```
发布：<提交短号> <提交标题>
发布点：<RELEASE_ID>
服务：active，/api/health ok，/api/overview 有当期周
回滚命令：bash deploy/release.sh --rollback <RELEASE_ID>
```

失败时改为：失败在哪一步、已回滚到哪个状态、把 `journalctl -u shikar -n 100` 的相关行贴出来。
