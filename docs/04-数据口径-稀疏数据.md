# shikar · 稀疏 / 单快照数据的温度与阶段口径评估

> 类型：产品评估文档（**只评估口径，不改代码**）
> 版本：v0.1（2026-11-09）｜对应需求：[Issue #19](https://github.com/BeiFaXianLe/shikar/issues/19)
> 适用对象：后续实现「数据充足度分档」的开发者、以及用本看板做判断的用户本人
> 一句话结论：**当前只有 1 期的记录不足以判「下行 / 升温」等趋势阶段，应降级为「只给读数、不给结论」。** 本文件说明为什么、门槛怎么定、各页面怎么展示、以及实现清单与推荐方案。

---

## 0. 结论速览（先看这里）

1. **只有一年的数据，不能判「下行」。** 「下行 / 升温」这类**趋势阶段**必须由**同一小区、可比口径的多期序列**推出；单期快照没有任何时间前后的对比，谈不上方向。
2. 当前系统确实对**单期记录**也输出了 `temperature` 与 `stage`（本文实测库里 817 条单期记录被贴上温度，其中 455 条被判为「下行」），这是**过度解读**，须纠正。
3. 推荐口径：**趋势温度/阶段需要「≥ 3 期、且跨度 ≥ 1 年（建议 ≥ 2 年）、同一小区同口径、缺口不过大」**才启用；不足时全站统一显示**「数据不足 / 暂无」+ 原始读数**，口径上**不臆断**。
4. 落地分两档展示：**「数据不足」→ 只给读数；「数据足够」→ 才给温度/阶段并注明依据的期数与区间**。
5. 首页「温度总览 / 榜单 / 城市温度」在无足够数据时**不参与聚合**，宁可留空也不给结论。
6. 实现只改后端派生计算 + 首页聚合 + 少量前端空态，**不改数据结构**；近期（先看东西）成本很低，详见 §6。

## 1. 现状拆解：我们手里到底有什么数据

### 1.1 时间结构（以仓库内 `data/shikar.db` 实测为准）

| 维度 | 事实 |
|---|---|
| 小区总数 | **17,439** 个 |
| 只有 **1 期**的小区 | **16,301** 个（占 93.5%） |
| 有 **2 期**的小区 | **1,138** 个（占 6.5%） |
| 存在的期次 | 仅 **2019-02**（2019 链家全量快照，16,622 条）与 **2026-W46**（2026 房天下当期快照，1,955 条） |
| 两期之间的跨度 | **约 7 年零 9 个月**（2019-02 → 2026-W46） |
| 周度指标表字段 | `price / mom4 / mom13 / supply / vol30 / absorb / bargain / heat / temperature / stage` |

要点：

- **绝大多数小区只有一个时间点**——要么只有 2019-02，要么只有 2026-W46；跨两期的只有 1,138 个。
- 有 2 期的小区，其两期之间也不是「连续周」关系，而是**相隔近 8 年的两个孤立点**，中间 7 年多是空白。
- 库中 `vol30`（近 30 天成交）、`bargain`（议价空间）、`heat`（关注热度）**基本为空**；`absorb`（去化率）也无从计算。**唯一普遍存在的「时间性」数字是价格，以及平台提供的「近月环比」。**

### 1.2 「近月环比」到底是什么

房天下当期快照每行带一个平台给的**「近月环比」**（CSV 字段 `mom1_pct`，单位 %）。它是**平台口径的两个月之间的价格对比**，回答的是：

> 「这个小区的挂牌均价，这个月比上个月，大概涨/跌了几个百分点。」

它的局限非常明确：

- 它是**两个相邻月份**的短窗口对比，**不是一条时间序列**；
- 它是**平台自己的口径**（挂牌价、取样范围、去重方式都由平台决定），与我们看板的「周度小区级」口径不同；
- 它**只能说明「最近一个月在动」，说明不了「处在周期的哪个阶段」**——比如一个人这个月比上个月轻了 0.5 kg，不能据此判断他是在「减肥期」还是「增肥期」。

> **一句话：「近月环比」是「两点之间的斜率瞬间值」，不是「多期趋势阶段」。** 二者绝不能混用（详见 §4 术语）。

### 1.3 当前代码为什么会给出「下行」（根因）

这是本单的核心问题，代码上能精确定位（**本文只描述、不修改**）：

- 建库脚本 `scripts/build_db.py` 对 **2026 当期**记录这样算（约第 90–118 行）：
  1. 取平台的 `mom1_pct / 100`，**直接当作 `mom4`**（本应是「4 周价格动量」）；
  2. 以**城市内所有小区的这个环比值**做 `percentile_normalize` 分位归一化；
  3. 其余三分项 `absorb / bargain / heat` 全部硬编码为中性 `50.0`；
  4. 于是 `compute_temperature({"mom4": n_mom, "absorb":50,"bargain":50,"heat":50})` 得到温度，`classify_stage(temp, mom)` 得到阶段。

- 结果：一条**只有 1 期**的记录，只要平台给的近月环比是**负的**，归一化后 `n_mom` 偏低 → 温度落在 25–55 → `classify_stage` 以 `mom4 < 0` 判为 **「下行」**；环比为正则判「升温 / 温和」。

- 实测分布（库内）：
  - 16,301 条单期记录中，**817 条被写入了非空温度**；其中 **「下行」455 条、「升温」286 条、「温和」68 条、「降温」8 条**。
  - 这 817 条的「温度」**几乎完全由一个近月环比决定**（另外三项恒为中性 50），并非多期趋势。

**结论：这不是数据的问题，而是「用 1 个月的两点斜率冒充了多期趋势阶段」。** 用户提出的「只有一年数据凭什么判下行」，问得完全正确。

### 1.4 详情页的现状（好消息：前端已部分纠偏）

前端 `web/app.js` 的小区详情页**已经**做了「期数 < 2 就不给温度/阶段、不画折线、只显示读数」的处理（`renderDetailHead` 用 `dp >= 2` 做闸门；`renderSeriesSection` 在 `dp < 2` 时只给「参考均价 / 近月环比 / 在售套数 / 数据周」和一句「数据不足……暂不给温度与趋势判断」）。

**但是**：

- 这只是**前端展示层**规避，**后端仍在给单期记录写 `temperature` / `stage`**；
- **首页并未纠偏**：`backend/shikar/overview.py` 的 `_latest_row` 取「最近一条 `temperature` 非空」的行参与聚合，**单期记录的温度照样进了「城市温度」「最热 / 最冷榜」**；
- 也就是说：详情页「看起来对了」，但**数据口径本身没对**，首页榜单被单期温度污染。

这也说明：真正的修法应在**数据口径层（后端派生 + 首页聚合）**统一，而不是各页面各写一遍。

## 2. 「足够数据」的定义（门槛与理由）

### 2.1 术语先对齐：什么叫「一期」「可比」

- **一期（data point）**：某小区在某一个时间点（某一周 / 某一月 / 某一年快照）的一组同口径指标。
- **可比口径**：同一小区、同一指标定义（如都是「挂牌均价」）、同一取样范围，才允许前后比较。**2019 链家快照与 2026 房天下快照是两个平台的口径**，严格来说二者并不同源；把它们当成「同一条序列的两个点」本身就有口径漂移风险（见 §2.3 的提示）。

### 2.2 判「趋势阶段」的最低数据门槛

建议设置三道闸，**全部满足**才允许输出温度 / 阶段：

| 门槛 | 建议阈值 | 理由 |
|---|---|---|
| **期数下限** | **≥ 3 期** | 2 个点只能连一条直线，「先跌后涨」与「持续下跌」在 2 点上无法区分；≥ 3 期才谈得上「形状」与「方向是否延续」。若必须给硬底线，则 **≥ 2 期仅为「可算差值」、≥ 3 期才「可判阶段」**。 |
| **最小时间跨度** | **≥ 12 个月**（理想 **≥ 24 个月**） | 房产是低频、慢变量市场，一个季度的波动多为噪声；要看「周期阶段」，至少需要覆盖一个完整的年度旺淡季，才能剔除季节性。跨度太短的「多期」其实是同一轮行情的高频采样，判不出阶段性。 |
| **时间连续性** | **相邻期缺口 ≤ 1 年**，且**覆盖区间内的期数满足「期数下限」** | 若两点之间空了 7 年，那只是「两段互不相关的快照」，不是一条连续的走势；「2019 一个点 + 2026 一个点」不能因为「有 2 期」就算够。 |

> 对照现状：现有 1,138 个「两期」小区是 **2019-02 + 2026-W46（跨约 7.75 年、中间全空）**。按上表，它们**期数够 2 但连续性 / 最小跨度虽达标、却只有 2 个孤立点 → 只能算「可算一段长周期差」，不足以判短期阶段**。**建议这 1,138 个至多降级为「对比型读数（2019 vs 2026）」，而不进入「温度/阶段」判定**，直到积累到连续 ≥ 3 期。

### 2.3 同源 / 同口径提示（重要）

- 现有两期来自**两个不同平台（链家 2019 / 房天下 2026）**，跨平台比较存在**口径漂移**（挂牌价 vs 成交价、是否含车位、楼层折算等）。因此即使「期数」达标，也应标注「跨源，口径可能不完全一致」。
- 未来若开新数据源，应**优先统一到同一平台的历史序列**，或用重叠期做**口径校准**后再拼接。

### 2.4 门槛的「分档」表达

把上述三闸落到一个可执行的档位枚举（后续实现按此返回 `data_sufficiency`）：

| 档位 | 条件（建议） | 允许输出 |
|---|---|---|
| `insufficient`（不足） | 期数 = 1，或缺失严重 | 仅原始读数（均价 / 近月环比 / 在售套数 / 建成年 / 数据期数），**不输出温度、阶段、趋势** |
| `limited`（有限） | 期数 = 2，或缺口过大 / 跨度不足 | 可给「两期对比读数」（如 2019→2026 涨跌幅），**仍不输出趋势阶段**，标注「样本有限」 |
| `sufficient`（足够） | 期数 ≥ 3 且跨度 ≥ 12 个月且缺口 ≤ 1 年 | 输出温度 / 阶段，并注明「依据 N 期，区间 YYYY-MM～YYYY-MM」 |

## 3. 分档展示规则（页面级）

原则一句话：**不臆断——宁可显示「数据不足 / 暂无」，也不给结论。**

### 3.1 小区详情页

- **数据不足（`insufficient`，如仅 1 期）**
  - **只展示原始读数**：参考均价、近月环比、在售套数、建成年（若有）、数据期数；
  - **不输出温度、不输出阶段、不画趋势折线**（单点折线空洞无意义）；
  - 文案用固定提示：「数据不足（仅 1 期），以上仅为读数，暂不给出温度与趋势判断。」
  - —— 此档与现行 `web/app.js` 的稀疏态基本一致，可复用现有实现。
- **有限（`limited`，如 2019 + 2026 两期）**
  - 可给「两期对比」读数：例如「2019-02 均价 ¥X → 2026-W46 均价 ¥Y（约 −Z%）」，明确写清**两个时点**与**跨源口径提示**；
  - **仍不输出「下行 / 升温」等阶段标签**，温度置空；
  - 文案提示「仅有 2 个时点，样本有限，仅供参考」。
- **足够（`sufficient`）**
  - 才输出温度与阶段；
  - **必须注明依据**：「依据 N 期，区间 2019-02～2026-W46」；
  - 折线图正常展示，并在图下标明数据点数。

### 3.2 首页「温度总览 / 榜单 / 城市温度」

- **城市温度**：只对 `sufficient` 小区求均值；若某城市**没有任何** `sufficient` 小区，则城市温度显示 **「暂无足够数据」**，而不是拿单期温度凑一个数。
- **最热 / 最冷榜**：只纳入 `sufficient` 小区；不足者不进榜。若全城无足够数据，榜单显示 **「暂无」**。
- **升温最快 / 降温最快榜**：本就需要 `mom4`（多期动量），单期无 `mom4` 者一律排除（**现状 `top_rising / top_falling` 已要求 `mom4` 非空，方向正确，但 `mom4` 的来源要改为「真正的多期动量」而非近月环比**）。
- **总览页**：显式提示「本城 X% 小区数据不足，暂无温度」，让用户知道「空」是因为「没有足够数据」而不是「数据坏了」。

### 3.3 边角与一致性

- **同一小区在不同页面口径必须一致**：详情页说「数据不足」，首页榜单就不应把它当作有温度的小区。
- **筛选 / 排序**遇到无温度的小区：默认排在最后或用「—」，**不用 50 分中性值假装有温度**（现状温度用 `percentile_normalize` 不足时回退 50.0，会被误当成「真实中性温度」，须在展示层区分「暂无」与「50 分」）。

## 4. 术语与文案统一建议

### 4.1 两个概念必须分清

| 术语 | 含义 | 数据要求 | 能回答的问题 | 不能回答的问题 |
|---|---|---|---|---|
| **近月环比**（`mom1_pct`） | 平台口径的**相邻两月**挂牌价涨跌幅 | 2 个月（平台已给） | 「最近一个月在涨还是在跌？」 | 「处在周期什么阶段？」「趋势会不会延续？」 |
| **趋势阶段**（`stage`：下行 / 升温 / 温和 / 冰点 / 过热 / 降温） | 由**同一小区多期序列**的温度水位 × 动量方向判出 | **≥ 3 期、跨度 ≥ 12 个月** | 「处在上行 / 下行周期的哪一段？」 | 「下个月具体涨跌多少？」（那是预测，本产品不做） |

### 4.2 统一文案

- **禁止**把平台的近月环比直接标注为「温度」「阶段」「趋势」。详情页现有的「近月环比」标签是对的，保持；但**不要因为它为负就在旁边挂「下行」徽章**。
- 单期 / 数据不足时，温度与阶段位置统一显示 **「数据不足」**（详情）/ **「暂无足够数据」**（首页聚合）。
- 输出阶段时，必须**同时**呈现依据，例如：「阶段：升温 · 依据 6 期，区间 2024-01～2026-W46」。
- 页脚 / 指标说明补一条：「温度与阶段需要至少 3 期可比数据方可计算；仅 1 期时只展示原始读数。」

### 4.3 给用户的一句话解释（可放在附录 / 免责）

> 「一个小区只有一年的挂牌价，就像只看了股价一天的走势——能说今天在跌，不能说进入了熊市。趋势阶段需要连续若干个时间点才能判断。」

## 5. 影响面与风险（评估，不改代码）

- **影响用户判断的正解**：单期「下行」标签消失，用户不再被「只有 1 期却判下行」误导——这是本单要解决的根本问题。
- **会让首页「看起来变空」**：若严格按 `sufficient` 过滤，目前**几乎没有**小区满足 ≥ 3 期连续序列，首页温度 / 榜单可能大面积显示「暂无」。这正是**真实情况**，但需要在 UI 上讲清「为什么空」（见 §3.2 提示），否则用户会以为看板坏了。**这是本方案最主要的体验代价**，须在分期里先解决「空态解释」。
- **口径风险**：2019/2026 跨平台拼接的口径漂移（§2.3），须在「有限档」文案中显式提示。
- **不涉及**：不改数据库结构、不改公开 API 字段名（只是让不足时字段为 null）、不改合规红线。

## 6. 实现清单与工作量（**只列清单，不实现**）

> 下列改动均为「让口径正确」，非新增功能。分两期，PR 粒度小、可独立评审。

### 6.1 后端（核心，P0）

| 点 | 文件 / 函数 | 改动性质 | 说明 |
|---|---|---|---|
| 1 | `scripts/build_db.py`（约 90–118 行） | **改计算口径** | 不再把 `mom1_pct` 当 `mom4` 直接喂给 `compute_temperature/classify_stage`。**单期记录 `temperature`/`stage` 一律写 `None`**；`mom1_pct` 作为**独立字段/读数**保留（若表内无列，可仅在前端从 `mom4` 语义改名或新增 `mom1_pct` 展示口径）。 |
| 2 | `backend/shikar/pipeline.py::recompute` | **加门槛** | 重算阶段时，先算该小区的 `data_points` 与跨度；**不满足 ≥ 3 期 / 跨度 ≥ 12 月 / 缺口 ≤ 1 年 → `temperature=None, stage=None`**。 |
| 3 | 新增 `data_points` 输出 | **加字段** | 在 `storage.get_metric_series` 的返回或 `xiaoqu` 维度上暴露「数据期数」；API `GET /api/xiaoqu/{id}` 或 series 带出 `data_points` / `data_sufficiency`，供前端分档。 |
| 4 | `backend/shikar/overview.py::_latest_row` / `compute_overview` | **聚合过滤** | 只统计 `sufficient`（`temperature` 非空且 `stage` 非空且满足门槛）的小区；城市温度无合格样本 → `None`；榜单只纳入合格小区。 |
| 5 | 百分位回退中性值 | **语义区分** | 现状 `percentile_normalize` 样本不足返回 `50.0`（会显示成「真·50 分温度」）。展示层必须能区分「无温度」与「中性 50」，建议不足时**返回 `None`** 而非 `50.0`，或在派生阶段直接置 `None`。 |

| 7 | 首页空态（`web/app.js` 总览渲染 / `web/index.html`） | 城市温度 / 榜单无合格样本时显示「暂无足够数据」并附一句解释；温度缺失显示「—」而非 `50.0`。 |
| 8 | 文案与口径说明 | 引入 §4.2 的统一文案与页脚口径说明；把「近月环比」与「阶段」的区分写进指标说明。 |

### 6.4 工作量粗估（相对值）

- 后端改口径 + 门槛 + 字段：**小～中**（集中在 `build_db.py`、`pipeline.recompute`、`overview`）。
- 前端分档 + 空态 + 文案：**小**（详情页已有稀疏态可复用）。
- 测试补充：**小**。
- **数据重建**：改完 `build_db.py` 需 `python scripts/build_db.py` 重建 `data/shikar.db`（本地、秒级）。
- **结论**：若先只做「不足即置空 + 首页过滤 + 文案」（第 1、2、4、6、7 点），**完全可在一个小 PR 内完成**；「两期对比读数」「跨源口径提示」可作为二期增强。

## 7. 推荐结论

### 7.1 推荐方案

**短期（本单之后紧接着做）：只展示「近月行情」与原始读数，温度 / 趋势阶段在数据不足时一律置空、首页聚合排除不足样本。**
- 单期小区：只给均价、近月环比、在售套数、建成年、数据期数——**不给任何趋势结论**。
- 2 期小区：给「两期对比读数」，仍不给阶段。
- 只有满足 **≥ 3 期、跨度 ≥ 12 个月、缺口 ≤ 1 年、同口径** 的小区，才启用温度 / 阶段，并注明依据。

### 7.2 为什么这样最合理

- **诚实**：直接回应「只有一年凭什么判下行」——答案是「凭不了，所以不判」。
- **可执行**：不依赖新数据源，只改派生计算与展示口径，几天内可落地。
- **可扩展**：等历史数据积累到连续 ≥ 3 期，自动升级到「温度 / 阶段」，规则不用推翻重来。

### 7.3 代价（须让用户知情）

- **首页短期内会「变空」**：因当前几乎无满足门槛的小区，城市温度 / 榜单大概率显示「暂无足够数据」。这是**真实反映数据现状**，但必须配好空态解释，否则易被误解为故障。
- **损失了「当下有个温度数字」的视觉满足**：但这正是要避免的「虚假精确」。
- **跨源口径风险**：2019/2026 不同平台，拼接比较需提示口径可能不一致。

### 7.4 若坚持要「有个数字」

次优方案（**不推荐作为默认**）：把单期记录的温度像现在一样算出来，但**全站强制标注为「近月温度（仅供参考，非趋势）」并去色 / 降权**，且**不进入榜单聚合**。这样保留了「看个热闹」，但**必须让口径名称与视觉都与「趋势阶段」明显区隔**，否则又回到误导。相较之下，**建议默认采用 §7.1 的诚实方案**。
