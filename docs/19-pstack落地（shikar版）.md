# pstack 落地（shikar 版）

> 来源：Lauren Tan（@poteto）的 pstack v0.15.46（本机 `~/.claude/plugins/cache/cursor-plugins/pstack/0.15.46`，MIT）。
> 本文只收**已达成共识的四条**，并按 shikar 的仓库与角色改造；不照搬 cursor 的模型路由、`ketchup`、UI 控制类技能。
> 适用：shikar 全部研发、评审、验收工作。角色分工仍以 `docs/08-协作流程与角色.md` 为准。

## 0. 一页结论

要改的只有一件事：**把「能跑」换成「能证明」**。

| 过去 | 现在 |
|---|---|
| 谁写的谁说自己好了 | 验证另有其人，拿原始 brief 复跑 |
| 派单先写需求，完成条件靠猜 | 第一行就是目标 + 可判定的完成条件 |
| 一个 PR 一大坨，绿了就算过 | 小步提交，每步以一次真实检查收尾 |
| 同一个错再写一条规范 | 同一个错固化成测试/探针/校验 |

## 1. 规则一：验证权独立于开发权

**规则**：写代码的人不给自己签字。每条 PR 的「可合并」结论，必须来自没参与实现的验证者。

**怎么落**

- 开发方交付 = 分支 + PR + 自测证据，**不写「已验证」结论**；PR 正文里可以有「我跑了什么」，但不能有「可以合并」。
- 验证方独立检出，不在开发分支上改文件：

  ```bash
  git worktree add ../shikar-review-<pr> agent/<branch>
  cd ../shikar-review-<pr>/backend && python -m pytest
  ```

- 验证方拿到三样东西：**原始 brief、被验分支、上一轮报告**；不看开发者的口头解释。
- 验证必须跑真实产物：真实 HTTP 服务、真实数据或与生产同构的夹具。**单测绿不等于功能对**——反例见 `docs/20`：256 个测试全过，6 个并发请求挂 4 个。
- 修复轮次换人不换脑：新一轮交给全新 agent，带原始 brief + 上一轮报告 + 分支；旧会话只用来接没提交完的现场。

**完成条件**：验证报告里每一条「通过」都附命令与实际输出摘要，第三人能原样重放。

## 2. 规则二：目标 + 完成条件写进开工第一条

**规则**：任何派单、PR 描述、「开工」消息的第一段，固定两行——目标、完成条件。都用可判定的句子，不写形容词。

```
目标：<一句用户可感知的变化>
完成条件：
- <可观测断言 1>（怎么验：命令 / 接口 / 页面）
- <可观测断言 2>（怎么验：……）
不做：<明确排除项>
```

**怎么落**

- 缺「完成条件」的派单，接单方先退回补全，不进入实现。
- 缺「完成条件」的 PR，不进评审队列。
- 完成条件必须能被验证方独立执行；「体验更好」「性能更优」不算，要写成「首屏 < 1.5s（`curl -w`，冷缓存 3 次取中位数）」。

**完成条件**：仓库里每一条进行中的 PR，正文首段都能直接回答「做完长什么样、怎么验」。

## 3. 规则三：小步、每步可验、PR 带证据

**规则**

1. 一个提交只做一件可验证的事；合并顺序按依赖排，不按提交时间排。
2. 每个可验证单元以一次真实检查收尾（测试 / 探针 / 页面），不通过不进入下一步。
3. PR 正文必须有「证据」段：命令、结果、失败样本。截图不能作为唯一证据。
4. 数字必须能解释：报「快了 / 降了 / 覆盖了多少」时给出测量口径、基线、以及它测的确实是这件事的证明。

**怎么落**

- 证据格式固定（可直接复制）：

  ```
  ## 证据
  - `cd backend && python -m pytest` → 256 passed，退出码 0
  - `python scripts/review/commute_probe.py` → A/B/C 三项见输出
  - 真实接口：`curl -s 'http://127.0.0.1:8000/api/commute?...'` → 200，items=20
  ```

- 验证方对 PR 声称的每条结论**逐条复跑**，不复跑就不写「通过」。
- 分支落后主干时先 rebase 再验：落后期间的改动会改变结论（`docs/20` 的 P2-7 即此类）。

**完成条件**：任取一条已合并 PR，第三人只看正文就能重放全部证据并得到同样结论。

## 4. 规则四：重复错误固化成结构

**规则**：同一条规范被写第二次之前，先问能不能变成拦截。**规范产能过剩、自动拦截不足**是当前主要浪费。

| 重复出现的错误 | 固化成 |
|---|---|
| 同一个 bug 第二次出现 | 回归测试 / 探针脚本（如 `scripts/review/commute_probe.py`） |
| 字段、口径、坐标系易错 | 类型、校验、schema、边界解析 |
| 流程步骤容易漏 | CI 检查、PR 模板、脚本 |
| 只能靠人记的约定 | 代码结构（默认值、封装、单一入口） |

**禁止**：往 `docs/` 再加一条「请注意……」。

**完成条件**：每月回看，`docs/` 新增条目数 ≤ 新增自动化检查数；否则下个月先补检查再写文档。

## 5. 三段式审核模板（本仓库唯一审核格式）

每个问题四项必填：**等级、位置、现象、证据**；再加风险与建议。

**等级**

| 等级 | 含义 |
|---|---|
| P0 | 数据损坏、安全、资损、不可恢复 |
| P1 | 主流程不可用，或稳定给出错误结果 |
| P2 | 验收前应修；不阻断合并，但必须有处置结论 |
| P3 | 改进项，可接受风险 |

**硬规则**：**P0/P1 没有复现路径，自动降级为「建议改」**。不允许用「我认为」「一般来说」定级。

**三段式**

1. **必改（P0/P1）**：每条附复现路径（命令或步骤）+ 实际输出。缺一即降级。
2. **建议改（P2）**：写清影响面与处置（本轮修 / 转 issue / 明确接受）。
3. **可接受风险（P3 或明示豁免）**：写清为什么不修、什么条件下需要重看。

**结论行固定三选一**

- `可合并`
- `修完可合并`（列出必改项编号）
- `不可合并`（说明是设计问题还是实现问题）

## 6. 任务类型与完成条件（只保留 6 类）

| 类型 | 产出 | 完成条件 |
|---|---|---|
| investigation | 结论 + 证据 | 每个结论能指到代码/数据/运行输出；不确定的明确标为推断 |
| bug-fix | 分支 + 失败用例 + 修复 | 先有能复现的失败用例，修复后同一用例通过；根因写在 PR 里 |
| feature | 分支 + 验收口径 | 完成条件逐条可验；新增接口有契约与错误码 |
| refactor | 行为不变的 diff | 重构前后同一组用例结果一致；无行为变化的证据 |
| babysit | 可合并的 PR | 冲突解决、CI 绿、每条评审意见有回应 |
| shipping | 合并后的主干 | 合并后主干复跑通过；回滚路径明确 |

## 7. 落地节奏

1. **试点**：PR #32 用本模板首审，报告见 `docs/20`，复现脚本 `scripts/review/commute_probe.py`。
2. **下一轮**：每条 PR 由非作者验证；重复问题转成测试或探针，不再新增规范条目。
3. **每月回看**：新增规范条目 vs 新增自动检查，后者不少于前者。

## 8. 明确不采纳

- cursor 的模型路由表与 model slug 体系（我们是 Orca bot 群，不复制 cursor 的模型配置）。
- `ketchup` / `ketchup-video` / `make-bot-ui` / `control-ui` 等展示与 UI 控制类技能。
- `setup-pstack` 写 rules 文件的机制。
- 22 个 playbook 全量照搬：只保留上面 6 类映射，避免再造一套没人查的目录。
