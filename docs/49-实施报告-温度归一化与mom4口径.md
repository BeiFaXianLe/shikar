# 实施报告 · 温度归一化与 mom4 口径

> 分支：`fix/temp-mom4-honest`｜日期：2026-11-23｜对应：g-shikar#108 / #183、排查报告 `docs/45-数据排查报告-线上四榜全空.md`
> 性质：**只改代码与派生指标计算口径**，不动 `data/*.csv` 原始数据、不改数据库结构、不改备份仓库。

## 1. 一句话结论

温度恒 50.0 不是「数据不够」，而是**公式把缺席的三项按 50 分计入**；`mom4` 也不是「4 周动量」，而是**同一小区序列里前第 4 条记录**（跨度 0 行 ≤35 天、170 行 >400 天）。本次把两处口径改成「缺失不参与」「按日历 4 周对齐」，并顺手修了 ratio 精度与备份缺文件静默成功。

**代价要说清**：按现库数据修完，那 6 个「合格」小区的温度会从假的 50.0 变成 **`NULL`（数据不足）**，四榜回到空态。这不是回归，是把编造的中性值撤掉——详见 §4 实测。

## 2. 关键线索复核：「已经跑了四周数据，为什么温度还是 50」

逐条核过数据链路，结论是**「周更跑过，但有效周次只有 2 期，而且旧口径下 4 期也永远算不出」**：

| 疑点 | 实测 |
|---|---|
| 周更快照到底有几期 | 本地 `data/fang_2026.csv` 与线上 `/opt/shikar/data/fang_2026.csv` 都只有 **2026-W46（1955 行）+ 2026-W48（1875 行）**。W47 没有采到；PR#38 之前的去重键不含 `week`，更早的周次每周都被当重复丢弃——所以「跑了很多周」但只留下 2 期。 |
| 历史成交样本进没进库 | 进了：`fang_preview_all.csv`（1014 行 / 406 小区）经 `ingest_history.py` 变成 762 个「小区×月」行。但它是**月粒度**（`week` 字段是 `YYYY-MM`），每个小区**最多 4 期**。 |
| 为什么 4 期还不产生 mom4 | 旧实现要求 `i >= 4`，即**前第 4 条记录 = 至少 5 期**。4 期数据在结构上永远算不出 mom4。 |
| 为什么「温度不该全是 50」的直觉是对的 | 4 期月数据若按「4 周前」对齐（月间隔约 30 天，落在 28±7 天窗口内），第 2–4 期都能算出 mom4——只是旧口径要第 5 期。 |
| 还有一个隐藏覆盖 | `build_db.py` 曾把平台给的「近月环比」`mom1_pct` 直接当 `mom4` 写库（docs/04 §1.2 已指出这是两个概念），随后 `recompute_metrics.py` 又用「前第 4 条」口径把它覆盖成 NULL/跨年差值。两个写入方各算一套，必然漂移。 |

## 3. 改动清单

| 文件 | 为什么改 |
|---|---|
| `backend/shikar/scoring.py` | `compute_temperature` 改为**只对可用分项加权**：`Σ(w·s)/Σw`，键缺失或为 `None` 的分项既不进分子也不进分母；`bargain` 仍取 `100-n`。四个分项齐全时与旧公式逐值等价；全缺时仍返回 50.0（纯函数回退），由调用方决定是否写成 `NULL`。 |
| `backend/shikar/pipeline.py` | ① 新增 `_mom4_series`：`mom4 = price_t / price_{4周前} - 1`，在 **28±7 天（21–35 天）** 窗口内找最接近 28 天的一期做基准，找不到即 `None`；② `_percentile_series` 样本不足时返回 `None`（不再返回中性 50）；③ `recompute` 只把有值的分项传给温度，**一个可用分项都没有时 `temperature=None`**，不编造 50。 |
| `scripts/build_db.py` | 只写原始数据（价格/供应），**派生列一律留空**交给 `recompute_metrics.py`；不再把 `mom1_pct` 当 `mom4`，也不再自带一份温度计算。口径从此只有一份实现。 |
| `backend/shikar/overview.py` | P1-2：`insufficient_ratio` / 分区 ratio / `delta_insufficient_ratio` 由 3 位改 4 位。**更正排查报告的表述**：前端 `web/app.js` 并不读 `insufficient_ratio`，只渲染 `insufficient/total` 计数，所以这条**用户侧没有可见变化**，只是 API 数值更准（不虚报「已修前端」）。另同步 `_prev_row` 注释，说明它与 mom4 不是同一口径。 |
| `scripts/backup_critical.py` | P3-2：完整性门覆盖**文件 + 库 + 四张不可再生表**（只查 CSV 会放行「库/表丢了」的备份，而推送是 force push，会把异地唯一那份 `db.sql` 覆盖成空）；不完整时返回非零、只产出 `partial-<ts>.tar.gz`，`push_backup.py` 只挑 `critical-*.tar.gz`，推不上去。 |
| `deploy/refresh.sh` | 备份返回非零时**跳过异地推送**（原来无论备份是否完整都会推送）。 |
| `backend/shikar/main.py` | demo 造数：`_DEMO_WEEKS` 10→15、期次步长 13 周→**28 天**，并给周增量加确定性波动（相位随小区错开）。旧 demo 每期 91 天，改日历口径后 mom4 全空、`--seed` 首屏四榜全空；15×28=392 天既过门槛又落在 4 周窗口内。另：纯线性价格会让每个小区的 mom4 恒定、百分位恒 50，温度又变成同一个值（最热=最冷），所以增量必须带波动。 |
| `web/app.js` | 两处文案：`近月 …` → `近4周 …`、`近月环比` → `较4周前`，与 mom4 的真实含义一致（不再把「前第 4 条记录」或平台月环比说成近月）。 |
| `backend/tests/*`、`docs/04`、`docs/45`、本文件 | 测试与口径同步；`docs/45` 为本次修复依据的排查报告，随 PR 入库便于评审复现。 |

接口兼容性：`/api/overview`、`/api/catalog` 的字段名一个没改，只改数值口径（`temperature` 可能为 `null`，前端已有「数据不足」空态路径）。

## 4. 数据影响实测（现库副本，不是生产）

用线上同源副本 `shikar.db`（21214 行）在**副本**上跑新代码的 `recompute`：

| 指标 | 改前 | 改后 |
|---|---|---|
| `temperature` 非空行 | 27（**全部恰好 50.0**） | **0** |
| `mom4` 非空行 | 262 | 191 |
| 四榜 | 最热=最冷、升温=降温（同批小区正反排） | 空（无合格温度） |

再往下拆，为什么改后是 0 而不是「有分布」：

| 假设口径 | 合格小区 | 能算出温度的行 |
|---|---|---|
| A. 现门槛（≥3 期、跨度 ≥365 天、缺口 ≤365 天） | 6 | 0 |
| B. 去掉跨度要求（≥3 期、缺口 ≤365 天） | 6 | 0（2019-02 造成的 7 年缺口仍被拦下） |
| C. 最长连续段判定（P1-3） | 22 | 0 |
| D. 现门槛 + 4 周年化 | 6 | 0 |

根因是一条硬约束：**要算百分位至少要 4 个 mom4 样本，也就是同一小区至少 5 个「4 周对齐」的连续期次**；而现库里满足「跨度 ≥365 天」的序列都是稀疏的（月粒度甚至跨年），凑不出 4 个连续 4 周样本。所以：

- 想看到温度，**要么继续按周累积**（连续 4 周快照就能算 mom4，但现门槛还要跨度满 1 年）；
- **要么改门槛/归一化口径**（产品决策，见 §6）。

这次没有为了让榜单「看起来有内容」而放宽任何门槛——那正是排查报告里说的「比空榜更危险的假的有」。

## 6. 未做 / 待产品决策（不自行拍）

1. **门槛要不要为周更数据放宽**（P1-3 + 跨度）：建议「取最长连续段判定，段内 ≥3 期、缺口 ≤365 天」，并对**连续周更**序列把跨度要求降到 ≥8 周；「趋势阶段」仍保留 ≥1 年的高门槛。这决定温度什么时候能真正铺开，属口径定义，需确认。
2. **归一化样本来源**：现在仍是「小区自身历史」，PRD §6.2 原本写的是「城市内 52 周滚动百分位」。切换成同城横截面能让稀疏数据也有分布，但温度语义会从「跟自己比」变成「跟同城比」，需确认。
3. **P1-1 无方差护栏**：温度全相同（或全空）时抑制四榜并给 `boards_suppressed` 标记。本次温度全空，四榜自然为空，护栏可另开单。
4. **温度口径（复审 P2）**：缺分项时温度=「该小区自身历史分位」，跨小区比大小意义弱；若要真正可比，需 `temperature_basis` 标注或改同城同期横截面。
5. **`push_backup.py` 单调保护**与 **`partial-*` 轮转/list**：与 P3-2 同源，建议单独一单。
6. **P2-1 分母口径**（3,724 个零价格小区计入 total）、**P2-2 supply 两种语义**、**P2-3 扩抓取页数**、**P3-1 同名重复**：均未动，按报告优先级排期。

## 7. 风险与回滚

- **只改派生列**：`recompute` 幂等（纯 UPDATE、可重复执行），原始 CSV 与不可再生数据一个字节没动；失败时旧库仍在 `data/shikar.db.prev`。
- **线上生效需要重算**：代码部署后必须跑 `python3 scripts/recompute_metrics.py --db data/shikar.db`（`deploy/refresh.sh` 已包含该步），否则库里仍是旧的 50.0 —— 也就是说「上线 ≠ 生效」，要重算派生数据才生效。
- **行为变化**：`build_db.py` 单独跑完不再有温度（`data/README.md` 本来就要求随后跑 recompute，流程未变）；备份缺文件会返回非零，`refresh.sh` 会跳过推送并在日志里写明，不再静默。
- **可回滚**：整条改动是口径修正，回滚 = revert 本 PR 并重跑 recompute 恢复旧值；无 schema 变更、无数据删除。
