# 定时任务运维手册（抓数每周 + 版本对齐每日）

> 依据：宝拉 2026-11-23 在 shikar项目群的两条裁定 ——「数据抓取一周一次是为了防止限流，应用版本对齐应该每天一下」，
> 以及同日对方案的确认（05:20 时间、每日自动对齐、抓数加 2 小时超时）。
> 本文所有服务器事实为 **2026-11-23 实测**（命令与输出见 §10），不是转述、不是推测。
> 一句话：**抓数每周一 04:30（防限流），代码对齐每天 05:20（只搬已合并的 origin/main）；两套单元的源文件在 `deploy/systemd/`，用 `deploy/install-timers.sh` 装/卸/查。**

---

## 1. 两条任务速查

| | 数据抓数 | 应用版本对齐 |
|---|---|---|
| 单元 | `shikar-refresh.timer` + `shikar-refresh.service` | `shikar-release.timer` + `shikar-release.service` |
| 配置时间 | **每周一 04:30** | **每天 05:20** |
| 随机延迟 | `RandomizedDelaySec=900`（0–15 分钟）→ 实际启动 **04:30–04:45** | 无（发布要可预测） |
| 实际执行 | `deploy/refresh.sh`（抓数→采样→备份→重建库→回灌→重算→异地备份→重启） | `deploy/release.sh --yes`（拉取→对齐代码→pytest→重启→健康检查→冒烟，失败自动回滚） |
| 单次耗时 | 实测 11m45s ~ 12m00s | 有变更时约 1–2 分钟；无变更只做健康检查（秒级） |
| 超时 | `TimeoutStartSec=7200`（2 小时） | `TimeoutStartSec=1800`（30 分钟） |
| `Persistent` | `true`（关机错过，开机后补跑） | `true` |
| 为什么是这个频率 | 每城 100 页快照 + 京津 300/200 个小区详情页，一周一轮已接近「低频、限量」上限；每天跑等于 7 倍抓取量，限流不可控 | 合并后的代码要尽快上线，人不用每天手动发布 |

时区：两台都依赖系统时区 **`Asia/Shanghai`**（实测 `timedatectl` 为 CST+0800、NTP 已同步）。`OnCalendar` 按系统时区解释——**如果哪天系统时区被改成 UTC，抓数会变成 12:30、对齐变成 13:20**。`install-timers.sh status` 会在时区不对时打 WARN。

### 1.1 「04:30 还是 04:44」的旧账（已结案）

- 配置值就是 **`Mon 04:30`**（`deploy/systemd/shikar-refresh.timer`，与线上 `systemctl cat` 一致）。
- 旧文档 `部署盘点与迁移方案.md` 里的「04:44」是某周 **`systemctl list-timers` 的 NEXT 列**（= 04:30 + 随机延迟），是观测值，不是配置。实测：11-16 实际启动 `04:39:12`、11-23 `04:38:40`、下周 NEXT `04:35:30`——**每周都不同**。
- 结论：**别拿 `list-timers` 的 NEXT 当配置改**。要看配置就看 `deploy/systemd/*.timer` 或 `systemctl cat`。

## 2. 数据抓数（每周一 04:30）

### 2.1 它做什么

`deploy/refresh.sh` 的固定流水（每一步失败都不中断，只继续下一步）：

1. `scripts/fetch_fang.py --city bj|tj --pages 100 --delay 1.5` → 当期快照写 `data/fang_2026.csv`（键：城 + 小区 + ISO 周）
2. `scripts/sample_fang_preview.py --city bj --n 300` / `--city tj --n 200` → 随机采样详情页历史成交，**合并追加**到 `data/fang_preview_all.csv`
3. `scripts/backup_critical.py backup --keep 12` → `data/backups/critical-*.tar.gz`（CSV + 关键表，约 4.2MB/份）
4. 整库快照 `data/shikar.db.fullbak`（只留 1 份）
5. `scripts/build_db.py` → 原子替换 `data/shikar.db`，旧库留 `data/shikar.db.prev`
6. `scripts/ingest_history.py --csv data/fang_preview_all.csv` → 历史成交按「小区×月」中位数入库（只增不删）
7. `scripts/recompute_metrics.py` → 全量重算 mom4/absorb/temperature/stage
   ⚠️ **这一步不能省**：`build_db` / `ingest` 都不算温度，漏了会让 `xiaoqu_metric_weekly.temperature` 大面积 NULL、首页 `/api/overview` 聚合为空（2026-11-19 踩过，见 `data/SNAPSHOT_LOG.md`）
8. 再备份一次 → `scripts/push_backup.py` 推到私有仓库 `<owner>-data-backup` → `sudo -n systemctl restart shikar`

### 2.2 怎么判断这一轮成功（**别看 systemd 的 status**）

`refresh.sh` 里每个失败分支都是 `|| echo "… failed (continue)"`，脚本几乎**总是 exit 0**——`systemctl status` 显示 `Finished … status=0` **不代表数据成功**。看 journal 里的三条硬信号：

```bash
journalctl -u shikar-refresh -n 200 --no-pager | grep -E 'refresh done|DONE .*新增|推送完成|WARN|FAILED'
```

| 硬信号 | 期望 |
|---|---|
| `refresh done <时间>` | 有（说明跑完了） |
| `DONE 小区有成交 N/M，新增 X 行，累计 Y 行` | `X` 通常 >0；连续几周 `X=0` 要查抓取是不是被限流 |
| `推送完成` / `完成: https://github.com/<owner>-data-backup` | 有（异地备份成功） |
| 出现 `WARN:` / `FAILED` | 需要人看一眼（备份失败、推送失败、build_db 失败都会打出来） |

数据新鲜度（只读，任选一条）：

```bash
sqlite3 /opt/shikar/data/shikar.db "select max(week), count(*) from xiaoqu_metric_weekly where week like '20%';"
# 没有 sqlite3 CLI 时：
python3 -c "import sqlite3;c=sqlite3.connect('/opt/shikar/data/shikar.db');print(c.execute(\"select max(week),count(*) from xiaoqu_metric_weekly where week like '20%'\").fetchone())"
```

期望：`max(week)` **不早于本周**（周一抓数后前进一期）。若停在两周前，说明抓取被限流或脚本提前中断。

### 2.3 已知未解决（本轮明确没做）

- **没有失败告警通道**：仓库里只有 `.secrets/gh-token` 与 `baidu_ak.txt`，没有 webhook / 邮件 / IM。所以现在是「周一上午人自己看 journal」。要做自动告警需要先定渠道（例如用 gh-token 开 Issue，但要加 `issues:write` 权限）——列为后续 P2。
- 抓数与重建期间服务不停（`build_db` 是原子替换 + 最后 restart），首页可能短暂读到旧库，属设计如此。

## 3. 应用版本对齐（每天 05:20）

### 3.1 它做什么

`shikar-release.service` 只做三件事，真正的活全交给现成的 `deploy/release.sh`：

| 阶段 | 指令 | 为什么 |
|---|---|---|
| 拉取 | `ExecStartPre=git -C /opt/shikar fetch --prune origin` | `release.sh` 自己 fetch 失败会退回「本地已有引用」，会**报成功但没对齐**；无人值守不接受这种静默 → 拉不到就整单失败，宁可不发也不发旧版 |
| 前置条件 | `ExecCondition=/bin/sh -c '… ActiveState …'` | **抓数正在跑（active/activating/reloading/deactivating）就跳过今天这次**；跳过时 systemd 记为 `condition failed`，既不算失败也不误动线上 |
| 发布 | `/opt/shikar/deploy/release.sh --yes` | 幂等（同一 commit 不搬文件、只做健康检查）、发布点备份、服务端 pytest、`/api/health`、`/api/overview` 冒烟、**失败自动回滚**、只同步 `backend web scripts deploy`（**不碰 `data/`、`.secrets/`**） |

**对齐口径 = `origin/main`**，不是本机 main，也不是服务器上那个「内容正确但 HEAD 落后」的本地分支（见 `docs/发布与回滚.md` §1.1）。本机 main 若还有未推送提交，**不会**被这条任务带上线。

**只搬运、不决策**：不合并 PR、不改配置、不改仓库保护设置。合并仍由人点头。

### 3.2 怎么判断今天有没有对齐

```bash
# 1) 目标 = 服务器看到的 origin/main
git -C /opt/shikar rev-parse --short origin/main
# 2) 已部署 = 发布回执
grep COMMIT /opt/shikar/.deployed-release
# 3) 两者相同即对齐；不相同看下面
journalctl -u shikar-release -n 60 --no-pager
tail -3 /opt/shikar/.releases/history.log     # 每次真正发布都会追加一行
systemctl status shikar-release.service       # 看到 "condition failed" = 今天因抓数在跑而跳过
```

三种「没对齐」都是正常的：
- **没有新提交** → `release.sh` 幂等：不搬文件、不重启，只做健康检查，`history.log` 不追加；
- **抓数在跑** → 跳过（`condition failed`），第二天再对；
- **fetch 失败** → 整单失败（`Failed`），第二天重试；**绝不会**把旧版本当新版本发上去。

### 3.3 紧急处置

```bash
# 立刻对齐一次（手动，跳过 timer 等 05:20）
sudo systemctl start shikar-release.service
# 回滚到上一个发布点（人决定，助手不自动做）
bash /opt/shikar/deploy/release.sh --list
bash /opt/shikar/deploy/release.sh --rollback latest
# 暂停每日对齐（例如发现 main 上有问题、想先压住）
sudo systemctl disable --now shikar-release.timer
```

## 4. 安装 / 卸载 / 查看

安装器：`deploy/install-timers.sh`（幂等；源文件 `deploy/systemd/`，**唯一事实来源**）。

| 命令 | 作用 | 需要 sudo |
|---|---|---|
| `bash deploy/install-timers.sh status` | 是否安装、与仓库是否一致、时区、下次触发、最近一次运行日志 | 否（只读） |
| `bash deploy/install-timers.sh diff` | `/etc` 现状 vs 仓库单元逐行差异 | 否（只读） |
| `bash deploy/install-timers.sh install --dry-run` | 只打印将做什么 | 否 |
| `bash deploy/install-timers.sh install` | 写单元、`daemon-reload`、`enable --now`；内容一致则跳过写入 | 是 |
| `bash deploy/install-timers.sh install --force` | `/etc` 里有人手改过时强制覆盖（先留 `.bak-<时间戳>`） | 是 |
| `bash deploy/install-timers.sh uninstall` | 停用并删除 4 个单元（保留 `.bak-*`，**不动数据**） | 是 |

规则：
- 单元在 `/etc` 里与仓库不同、又没给 `--force` → **拒绝覆盖**（防止静默冲掉人工改动）；
- 覆盖前一定留 `/etc/systemd/system/<name>.bak-YYYYmmdd-HHMMSS`；
- 安装器**不会**替人跑任务（不会 `systemctl start shikar-refresh.service`）——手动采集会向不可再生的 CSV 追加数据，属不可逆动作，见 `docs/发布与回滚.md` §5。

首次安装后的一步确认：

```bash
systemctl list-timers --all | grep shikar     # 两行：refresh（下周一是 04:30+延迟）、release（明天 05:20）
systemctl is-enabled shikar-refresh.timer shikar-release.timer
```

## 5. 与发布、回滚的关系

- `deploy/release.sh`（人手动跑）与 `shikar-release.service`（每日自动）是**同一套逻辑**，只是触发方式不同；`deploy/refresh.sh` 是另一条线（数据）。
- **两条线都会 `systemctl restart shikar`**，而且 `release.sh` 的 `rsync -a --delete deploy/` 会替换**正在执行**的 `refresh.sh`（bash 是边读边执行）。所以：抓数运行中不要发布——现在由 `shikar-release.service` 的 `ExecCondition` 自动兜住；人手动发布前仍应自查：
  ```bash
  systemctl is-active shikar-refresh.service   # 期望 inactive
  ```
- 同一天两边都要动时：**先 release，再 refresh**（沿用 `docs/发布与回滚.md` §6）。
- 每日对齐失败会**自动回滚到发布前代码**并在 journal 报错，线上不会停在半成品状态；发布点留在 `.releases/<ID>/` 供排查（每个约 176KB，`release.sh` 超过 5 个只告警，删除是人的决定）。

## 6. 哪些东西这两个任务绝不能碰

| 路径 | 为什么不能碰 | 谁保护它 |
|---|---|---|
| `data/fang_preview_all.csv` | 逐周累积的历史成交，**丢一周就永久缺失** | `refresh.sh` 只追加；`release.sh` 不碰 `data/`；安装器只写 `/etc` |
| `data/shikar.db` / `.prev` / `.fullbak` | 248MB 级数据集，重建靠原子替换 | `build_db.py` 原子替换；`release.sh` 不同步 `data/` |
| `data/backups/critical-*.tar.gz` | 不可再生数据的备份（留 12 份） | `backup_critical.py` 只管轮换 |
| `.secrets/gh-token`、`.secrets/baidu_ak.txt` | 异地备份与 POI 的凭据（0600） | `release.sh` 明确不同步 `.secrets/` |
| `.releases/` | 回滚点 | `release.sh` 只增；安装器不碰 |

## 7. 停用与恢复

```bash
# 只停抓数一个月（比如要换数据源）
sudo systemctl disable --now shikar-refresh.timer
# 只停每日对齐（比如 main 上有问题要压住）
sudo systemctl disable --now shikar-release.timer

# 全部卸载（保留 .bak-*，不动数据）
bash /opt/shikar/deploy/install-timers.sh uninstall

# 恢复某次被覆盖前的单元
sudo cp /etc/systemd/system/shikar-refresh.timer.bak-20261123-153000 /etc/systemd/system/shikar-refresh.timer
sudo systemctl daemon-reload
```

停用不影响已有数据与站点；`shikar.service` 本身不受影响。

## 8. 唯一事实来源

| 对象 | 事实来源 | 说明 |
|---|---|---|
| 两套单元 | `deploy/systemd/*`（仓库） | 服务器 `/etc/systemd/system/shikar-*` 是**部署产物**，由安装器按仓库写入 |
| 抓数流程 | `deploy/refresh.sh`（仓库 main） | 服务器 `/opt/shikar/deploy/refresh.sh` 与仓库 main md5 一致（无漂移） |
| 发布流程 | `deploy/release.sh` | 每日对齐直接调用它，不复制逻辑 |
| 接口/服务 | `shikar.service`（服务器 `/etc`，未纳入本仓库） | 本次不涉及，保持现状 |
| 运维口径 | 本文 | 与 `docs/发布与回滚.md` 互补：那边讲「怎么发布/回滚」，这边讲「定时任务怎么装/看/停」 |

dsh 仓库的 `deploy/DEPLOY-shikar.md` 里 §3（定时任务）、§8（每週采样接入）已经过时（它写的是旧版 refresh.sh 流程、且把随机延迟的观测值当成配置讨论）——**降级为历史参考，不再作为口径**。本仓库不搬运该文档。

## 9. 已知未解决 / 后续可选

| 项 | 现状 | 需要什么才能做 |
|---|---|---|
| 失败自动告警 | 无渠道，只能人看 journal | 定渠道（GitHub Issue / webhook / IM）+ token 权限 |
