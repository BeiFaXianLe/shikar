# A 类稀疏门槛修复方案（temperature / stage 置空 + 首页数据不足标识）

> 状态：**待 Leader 确认，未开始编码。**
> 依据：`docs/04-数据口径-稀疏数据.md` §2.2/§2.4（门槛）、§3.2（展示）、§5 实施清单第 2/4/5 项；
> testWorker 35 例执行结果（A1/A2/A3 FAIL）。**不需要产品裁定**——这是已批准口径未落地。

## 1. 缺陷

现状 `pipeline.recompute` 只按 `min_history=4`（归一化样本数）决定分项是否回退 50，
**没有**「≥3 期 / 跨度 ≥12 月 / 缺口 ≤1 年」的充分性门槛：

- 单期小区被算成 `temperature=50`、`stage=温和`；
- `overview` 把这类小区当作合格样本计入城市均温与 `top_hot/top_cold`；
- 首页没有任何「数据不足」标识。

结果：城市温度被稀释（实测 44.4），且「无温度」与「中性 50」不可区分。

`scripts/build_db.py:209-218` 的 `sufficient()` 已实现同一门槛（仅用于 2026-W46 特算路径），
**本方案以它为唯一口径**，保证两条写入路径判定一致。

## 2. 口径（与 build_db 对齐，写死）

对某小区的指标期次集合 `ws`（升序，`YYYY-Www` 解析为日期）：

| 条件 | 阈值 |
|---|---|
| 期数 | `len(ws) >= 3` |
| 首末跨度 | `(ws[-1] - ws[0]).days >= 365` |
| 最大相邻缺口 | `max(gap) <= 365` 天 |

三条全满足才计算 `temperature` / `stage`；任一不满足 → 该小区所有期次
`temperature=None`、`stage=None`。
`mom4` / `absorb` 照常计算（它们是读数，不是结论）。

## 3. 涉及文件与修改点

仓库根 `D:\AI-workspace\狩猎\shikar`；新分支从 `origin/main` 拉出，**不基于 #32**。

### 3.1 `backend/shikar/pipeline.py`

1. 新增模块级常量与纯函数（与 build_db 同口径，便于单测）：

   ```python
   MIN_PERIODS = 3
   MIN_SPAN_DAYS = 365
   MAX_GAP_DAYS = 365

   def _parse_week(week: str) -> Optional[date]: ...      # "2026-W46" → date
   def is_sufficient(weeks: Iterable[str], *,
                     min_periods=MIN_PERIODS, min_span_days=MIN_SPAN_DAYS,
                     max_gap_days=MAX_GAP_DAYS) -> bool: ...
   ```
   非法/不可解析的周次忽略；去重后排序。

2. `recompute(...)` 新增三个关键字参数（默认取上表常量）：`min_periods`、`min_span_days`、`max_gap_days`。
   在 `series = storage.get_metric_series(...)` 之后、逐行循环之前：

   ```python
   sufficient = is_sufficient([r["week"] for r in series], ...)
   ```

   循环内：

   ```python
   if sufficient:
       temperature = scoring.compute_temperature({...}, weights)
       stage = scoring.classify_stage(temperature, mom4 or 0.0)
   else:
       temperature = None
       stage = None
   ```
   **仍写回 `mom4` 与 `absorb`**，`UPDATE` 语句不变（只是把两个字段写 NULL）。

3. `ingest(...)` 透传三个参数（默认不变），便于测试与脚本按需放宽；生产路径不传。

4. docstring 补门槛说明与「不满足 → None」的语义。

### 3.2 `backend/shikar/overview.py`

1. 新增 `_last_row(series)`：取 `week` 升序的最后一条（**不过滤 temperature**），用于判定
   「有数据但不足」。
2. `compute_overview` 的循环：
   - `row = _latest_row(series)` 仍用于取有温度的样本（合格小区）；
   - 另取 `last = _last_row(series)`；`insufficient = last is not None and last.get("temperature") is None`；
   - 把每个城市的 `insufficient` 计数累计；
   - `week` 改为所有 `_last_row` 的 `week` 最大值（无数据才 None），使「只有不足小区」时首页仍能显示数据周。
3. 城市输出新增字段（**只增不改**）：

   | 字段 | 含义 |
   |---|---|
   | `total` | 该城有数据的小区数（= 合格 + 不足） |
   | `insufficient` | 数据不足（temperature 为 None）的小区数 |
   | `insufficient_ratio` | `insufficient / total`，保留 3 位小数；`total=0` 时 0.0 |

   `count` 语义保持不变（有温度的小区数），`temperature=None` 时表示全城无合格样本。
4. 榜单：`top_hot` / `top_cold` 仍只取合格项；`top_rising` / `top_falling` **改为只取合格项**
   （§151：同一小区在不同页面口径必须一致，数据不足的小区不进首页榜单）。

### 3.3 `web/app.js`（最小提示）

城市卡片温度区：当 `temperature` 为 `null` 时显示「数据不足」；当 `insufficient > 0` 时在卡片底部
加一行「本城 {insufficient}/{total} 个小区数据不足，未计入均温」。
定位：`app.js:511` 附近的城市卡片温度渲染处；不改其它页面。

### 3.4 不动的部分

- `scripts/build_db.py` 的 2026-W46 特算路径（已合规，不碰）。
- `scoring.py` 的 50.0 回退（§199 的「展示层区分」由 overview 的 None 与前端文案承担）。
- `mom4` 序列推导、`absorb`、NULL 字段安全逻辑。

## 5. 影响面

- 首页：数据不足的城市/小区不再稀释均温、不再进入榜单；新增三个字段；`week` 语义扩展为「最近数据周」。
- 详情页：`web/app.js` 已有 `dp >= 2` 闸门，本次不新增逻辑（后端返回 None 时前端本就显示 `—`）。
- 其它接口：`/api/xiaoqu/{id}` 等返回的 `temperature/stage` 可能为 None，前端已有空值处理（`fmtNum`）。
- 数据层面：`refresh.sh` / `recompute_metrics.py` 走 `recompute`，自动继承门槛；无需迁移脚本。
