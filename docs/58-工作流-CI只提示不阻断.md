# CI 只作提示、不阻断合并（2026-11-25）

> 触发：宝拉「我根本无法手动合并，目前先把 ci 校验去掉，现在工作流还有比较多问题，先处理工作流问题，有 PR 就行」。
> 交付：PR #58（本文件随该 PR 进 main）；#56 / #57 已并入同一份 `ci.yml` 口径并转绿。

## 1. 结论先行

| 门禁 | 之前 | 现在 |
|---|---|---|
| `verify（pytest + 静态门禁）` | 失败 → job 红 → required check 挡住合并 | 失败 → 只打 `::warning::` + step summary，job 仍绿 |
| `shellcheck（发布脚本）` | 同上 | 同上 |
| `流程门禁`（PR 正文三段式 / 三态） | 栏位没填齐 → 红 | 只提示，不阻断 |
| `review-gate（审核范围报告）`（#57 引入） | 没报告 → 红 | 只提示，不阻断 |
| `依赖漏洞体检` | 本来就 `continue-on-error` + 仅定时/手动 | 未动 |

仍在跑、仍在出日志、仍能看出失败——只是不再把「合并」这条路堵死。

## 2. 关键取舍：不删 job，只让 job 恒绿

main 的分支保护是 `strict: true`，required contexts 三项：

```
verify（pytest + 静态门禁） / shellcheck（发布脚本） / 流程门禁
```

分支保护按 **job 的 `name`** 认 check。把 job 删掉的后果不是「不再拦」，而是 check **永不上报** → PR 永远停在 `Expected — waiting for status to be reported`，比红更死。

因此做法是：

1. 三个 job 的 `name` **一个字都不改**；
2. 把其中的检查步骤加 `continue-on-error: true`（job 结论恒为 `success`）；
3. 每个 job 末尾加一步，`if: steps.<id>.outcome == 'failure'` 时输出 `::warning::` 与 step summary，把「其实有失败」留在日志与 Summary 里。

想恢复阻断：去掉对应步骤的 `continue-on-error: true` 即可，不涉及其它文件。

## 4. 仍依赖人工 / 管理员才能收口的环节

| 环节 | 现状与处置 |
|---|---|
| 点 Merge | 只有人能点；CI 不再挡。三个 PR 现在都是 `mergeable: MERGEABLE` / `mergeStateStatus: CLEAN` |
| 分支保护 · required checks ×3 | 已恒绿，不再挡。彻底删掉这项要求需管理员：GitHub → Settings → Branches → `main` → 取消 *Require status checks to pass* → Save |
