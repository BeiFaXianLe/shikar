# shikar（狩鹿）· 代价与可行性分析

> 范围：北京、天津，小区级。版本 v0.1（2026-11-06）｜Phase 1
> 结论先行：**技术可行（高），合规是主要约束（中高），成本可控（轻量 MVP ¥15–30 万研发 / ¥500–3,000 运行/月）**。

---

## 1. 技术可行性：✅ 高

无技术硬门槛。所需能力（时序数据、地理下钻、图表可视化、定时采集）均为成熟方案。

**推荐技术栈**
| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js + TypeScript + Tailwind + ECharts（或 D3） | SSR/SEO、图表能力强、响应式 |
| 后端 | FastAPI（Python） | 与数据/算法同语言，迭代快 |
| 数据 | PostgreSQL + TimescaleDB（时序）+ Redis（缓存） | 时序聚合、按周/月滑动计算方便 |
| 采集 | 独立 collector 服务（可插拔 adapter）+ 定时任务 | 换源不改业务 |
| 部署 | 单机 Docker Compose（MVP）→ 云托管（增长后） | 成本低、可迁移 |
| 监控 | 采集成功率/数据新鲜度看板 + 告警 | 数据产品质量的生命线 |

---

## 2. 数据可行性：⚠️ 中（受合规约束）

- 京津小区数量量级：北京约 1.2 万+ 小区、天津约 6 千+ 小区（链家口径，需实测校准）。
- 数据体量：2 万小区 × 每周 1 行 × ~50 指标 ≈ 100 万行/年 → **存储很小（<5GB）**，计算无压力。
- 采集节奏：每周 1 次 / 低频；限速 1–2 QPS，单机 3–8 小时跑完一轮，**无需大集群**。
- 难点：**反爬、页面结构变更、来源授权**，而非数据量。

---

## 3. 合规可行性：⚠️ 主要风险点

| 风险 | 等级 | 依据 | 缓解措施 |
|---|---|---|---|
| 抓取贝壳/链家房源明细被判不正当竞争 | **P0** | 已有判例（推推99 等） | 不抓明细/图片；只取公开聚合指标；低频；回链来源；优先授权/公开数据集 |
| 违规采集个人信息（经纪人/业主电话等） | **P0** | 个保法 | 完全不采集任何个人联系方式 |
| 数据准确性 / 误导 | P1 | 用户决策依赖 | 标注数据来源与时间；「非投资建议」免责 |
| 金融信息合规 | P1 | 若给买卖建议 | 只做「数据参考」，不做荐股/荐房式结论 |
| 网页上线备案 | P2 | 境内服务器 | ICP 备案 |

**推荐的数据策略（按优先级）**
1. **首选授权/公开数据集**（社区整理的链家历史数据集、官方网签、统计局指数）；
2. **次选合规采集**：只采小区页**公开聚合指标**（均价/在售/成交套数/关注数），低频、遵守 robots、不存图片与房源明细、显著标注来源；
3. **禁止**：采集个人联系方式、批量导出房源库对外提供。

> 架构上把「数据源」抽象成 adapter 接口，MVP 用低风险源，未来可替换为持牌数据商（中指云等）。

## 4. 研发代价估算（MVP）

| 模块 | 内容 | 人天 |
|---|---|---|
| 产品/交互设计 | 信息架构、4 个核心页、视觉规范 | 8 |
| 数据采集与清洗 ETL | 采集 adapter、去重、口径对齐、小区主数据（京津约 2 万） | 20 |
| 指标与温度算法 | 归一化、加权温度、阶段判定、信号、回测页 | 12 |
| 后端 API | 小区/板块/城市聚合、对比、自选、搜索 | 15 |
| 前端可视化 | 温度仪表、趋势曲线、成交量、热力/排行、对比、推演 | 25 |
| 测试 / 部署 / 备案 | 用例、CI、上线 | 10 |
| **合计** |  | **≈90 人天** |

- 2–3 人团队约 **6–8 周**；1 名全栈约 **14–16 周**。
- 按 ¥1,500/人天外部报价 ≈ **¥13.5 万**；若由 SuperAgent 自动化开发，人力成本大降，但增加模型 token 成本 + 验收人力。

## 6. 风险登记（按严重度）

| 等级 | 风险 | 影响 | 应对 |
|---|---|---|---|
| P0 | 数据采集合规 | 可能被诉/下架 | 合规数据策略（§3），不抓明细 |
| P0 | 反爬导致数据断供 | 产品无数据 | 多源 + adapter + 数据新鲜度监控 + 降级展示 |
| P1 | 「温度」算法无回测=玄学 | 用户不信任 | 公开算法口径 + 历史回测 + 可解释分解 |
| P1 | 小区主数据不全/重名 | 下钻错乱 | 建立小区主数据表，人工校核重点小区 |
| P2 | 页面结构变更 | 采集中断 | 采集器容错 + 变更告警 |
| P2 | 性能/成本随用户增长 | 费用上升 | MVP 单机，按需上 CDN/缓存 |

---

## 7. 可行性结论与建议

1. **可行**：技术成熟、成本可控，2–3 人 6–8 周可出 MVP。
2. **成败在数据**：先用**合规/公开数据**跑通「温度」体验，别一上来就硬爬贝壳明细。
3. **建议分期**：
   - **M1**：京津小区级聚合指标 + 温度/阶段 + 小区详情 + 排行（P0）；
   - **M2**：多小区对比 + 自选异动 + 推演（P1）；
   - **M3**：扩指标/扩城市/账号体系/商业化（P2）。
4. **预算建议**：MVP 研发 ¥15–30 万（或 AI 自动化为主则主要为人力验收 + token），运行 ¥500–3,000/月。

## 8. 个人自用（零付费 · 本地）方案【本项目采用】

> 前提：**纯个人使用、不对外分享/不商用、不付费**。数据固定 **B 档（小区级聚合，不含逐套成交/房源明细/个人信息）**。

### 8.1 成本目标：≈ ¥0 / 月
| 项 | 个人版做法 | 成本 |
|---|---|---|
| 部署 | 本机 `localhost` 运行，不公网、不备案 | ¥0 |
| 数据 | 官方免费（统计局70城、住建委网签）+ 小区级公开聚合指标 | ¥0 |
| 采集 | 低频（每天/每周 1 次）、限速，模拟正常浏览 | ¥0 |
| 数据源/代理/云 | **一律不用** | ¥0 |

> 原 §5「商用多用户 ¥2,000–6,000/月」不适用于本项目，个人版可整段忽略。

### 8.2 合规边界（个人自用仍须遵守）
1. **不采集任何个人信息**：业主/经纪人姓名、电话一概不碰。
2. **不存图片与整段房源描述**：只存数值型聚合指标（均价/在售/成交套数/关注数）。
3. **不绕过技术保护**：不破解验证码、不逆向登录加密、不使用他人账号批量抓取（避免触及《刑法》285 条风险）。
4. **不对外提供**：不上公网、不分享导出、不做二次发布；一旦公开传播就从“个人”变“经营/传播”，风险性质改变。
5. **遵循 robots 与限速**：低频、可读页面、遇到封禁即停止。
6. **标注来源与时间**，页脚保留「数据仅供参考，非投资建议」。

### 8.3 结论
个人自用 + B 档数据 + 本地零成本，**法律风险低**（主要剩平台协议导致的封号/封 IP 风险），**运行成本近乎为零**，完全可行。数据“更细致”的需求在本档内通过**小区级聚合 + 多指标可视化**满足，不追求逐套明细。
