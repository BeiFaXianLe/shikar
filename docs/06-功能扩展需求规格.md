# shikar 功能扩展 · 需求规格（交付 Codex 实现用）

> 版本 v1.0（2026-11-09）｜适用：Codex / 其他编码代理
> 配套原型：`prototype/index.html`｜技术评估：`docs/05-功能扩展技术评估.md`
> 一句话：在现有「京津小区行情看板」上，增加 **地铁沿线 / 学校·医院·高铁 POI / 双点加权通勤** 三类「按条件找小区」能力，并重做筛选界面。

---

## 0. 实现者先读：现有工程与约束
- 仓库：`BeiFaXianLe/shikar`，本地个人自用，**零第三方依赖优先**（当前后端纯 Python 标准库 + SQLite）。
- 后端：`backend/shikar/`：`scoring.py`（算法）、`storage.py`（SQLite 仓储）、`sources/`（CSV/Mock）、`pipeline.py`、`overview.py`、`catalog.py`、`api.py`（stdlib `http.server`）、`main.py`（启动入口）。
- 前端：`web/`（原生 HTML/CSS/JS，无框架、无外链），视觉为「纸面年鉴」风（宋体标题、细线、朱砂/靛蓝）。
- 数据：`data/shikar.db`（17,439 小区；2019 全量含 `longitude/latitude`）+ `data/*.csv`；`scripts/build_db.py` 重建库。
- **不要**改动既有 `scoring/storage/sources/pipeline` 的语义；新增能力以**新增模块 + 新增表 + 新脚本**方式接入。

---

## 1. 目标与范围
目标：让用户能按「地铁 / 学区 / 医疗 / 高铁 / 通勤」条件筛出小区，并能查看学校、医院的明细与「周边小区 Top20」。
分三期（按此优先级实现）：
- **P1 地铁沿线**（零外部依赖，先做）
- **P2 学校 / 医院 / 高铁 POI + 明细菜单 + Top20**（需 POI 数据，见 §3）
- **P3 双点加权通勤**（需路径规划 API，见 §3）
不在本期：交易撮合、地图 3D、预测式房价、账号体系。

---

## 2. 用户场景（用于验收）
1. 「我要 4 号线沿线、对口小学 2km 内、附近有三甲医院的小区」→ 筛选出列表。
2. 「我想看病方便，哪几个小区离协和最近？」→ 医院明细 → 协和 → Top20 小区。
3. 「我和爱人分别在国贸、中关村上班，希望两边都别太远」→ 通勤页，均衡模式排序。
4. 「我更看重国贸（权重 70%）」→ 加权后排序变化。

## 3. 数据需求与来源
| 数据 | 字段 | 来源建议 | 说明 |
|---|---|---|---|
| 小区主数据 | id、name、city、district、plate、lng/lat、price | 已有 `data` | 2019 数据集含经纬度；2026 快照部分无坐标，需回填/映射 |
| 地铁线路/站点 | line、station、lat/lng、线路 polyline | 公开地铁 GeoJSON（高德/OSM/GitHub） | 免费 |
| 学校 | name、阶段（小学/初中/高中）、lat/lng、是否重点 | 高德/百度 POI + 重点校名单 | 「重点/等级」POI 不含，需名单 |
| 医院 | name、等级（三甲/二甲/…）、lat/lng | 高德/百度 POI | |
| 高铁站 | name、lat/lng | 高德/百度 POI（火车站类） | |
| 路径时间 | 驾车/公交 时间矩阵 | 高德/百度 路径规划 API | **需 Key，按量计费**；必须缓存 |

> 实现可先内置**模拟/离线数据**跑通全部交互（原型即如此），再接真实 API。

## 4. 数据模型（推荐：明细表 + 物化宽表）
### 4.1 明细表
- `poi(id, type, name, subtype, grade, lat, lng, district, source, extra)`
  - `type` ∈ {school, hospital, hsr}；`subtype` 学校用 {primary,middle,high}；`grade` 医院等级。
- `community_poi(community_id, poi_id, distance_km, rank_in_poi)`
  - 主键 (community_id, poi_id)；索引 `(poi_id, distance_km)`（用于 Top20）、`(community_id, type)`。
### 4.2 物化宽表（ETL 生成，首页筛选用）
`community_features(community_id, city, district, nearest_subway_line, nearest_subway_station, subway_distance_km, primary_count, primary_min_km, middle_count, middle_min_km, high_count, high_min_km, hospital_count, hospital_min_km, has_sanjiag, hsr_min_km, updated_at)`
> 宽表只放「筛选用得上的聚合值」；明细与排名查明细表。避免把每个 POI 摊成列。

## 5. 功能需求
### F1 地铁沿线（P1）
- 选择：城市 → 线路（可多选）→ 站点（可选）。
- 规则：
  - 「距站 ≤ R」：小区到站直线距离 ≤ R（默认 1km，可调）。
  - 「沿线」：小区到线路折线距离 ≤ R。
- 结果：列表显示「最近线路·站点·距离」，可按距离排序。
- **验收**：选「4号线 + 距站≤1km」只返回满足条件的小区；距离值可核对（球面距离）。

### F2 学校 / 医院 / 高铁（P2）
- **明细菜单**：
  - 学校：小学/初中/高中 三个 Tab；表格列「学校｜区｜类型｜辐射小区数｜平均距离」；点某学校 → 「周边小区 Top20（按距离）」。
  - 医院：表格列「医院｜区｜等级｜辐射小区数｜最近距离」；点某医院 → Top20 小区。
- **首页筛选**（与明细复用同一数据）：
  - 地铁线路 / 站点、学区阶段 + 最大距离、医院等级 + 最大距离、高铁最大距离。
- **验收**：Top20 顺序按距离升序；筛选条件联动结果；空结果友好提示。

### F3 双点加权通勤（P3）
- 输入：地点 A、地点 B、模式（驾车/公交）、权重滑杆（A 优先↔均衡↔B 优先）。
- 计算：`score = w·tA + (1−w)·tB`；均衡=w=0.5（可选：均衡用 `max(tA,tB)` 或几何均值，需在 UI 说明当前口径）。
- 排序：按 score 升序；显示 tA、tB、score。
- **成本控制**：先按 F1/F2 粗筛到 ≤ N 个候选（如 200）再算路径；OD 结果缓存（SQLite + TTL）。
- **验收**：改变权重后排序按公式正确变化；相同查询命中缓存不重复请求。

## 6. 界面重构要求（重点：现原型「筛选区太挤太丑」，必须重做）
> 目标：**一屏看清、渐进展开、结果优先**。
1. **默认只露 3 个主筛选**（城市、地铁线路、预算/价格区间）；其余「学区 / 医疗 / 高铁 / 通勤」放入**「更多条件」抽屉**，默认收起，展开后分组（组标题：地铁 / 学区 / 医疗 / 交通 / 通勤）。
2. **筛选改为「条件行 + 已选条件 chips」**：已应用条件以 chip 展示在结果上方，可单个删除；不要把所有滑杆平铺在一屏。
3. **分组卡片而非平铺 grid**：每组 2–3 项，留白充足；滑杆旁显示当前数值。
4. **结果行信息分层**：主行=小区名 + 价格；次行=地铁·学校·医院·通勤（弱化），避免拥挤；hover 才展开更多。
5. **结果区占主视觉**：筛选栏不要抢视线；移动端筛选收为「筛选」按钮弹层。
6. 视觉沿用「纸面年鉴」（宋体标题、细线、朱砂/靛蓝、无圆角卡），但**减少控件密度**。
7. 可用性：键盘可达、焦点可见、空态/错误态有解释。

## 7. API 设计建议（在现有 `api.py` 风格上扩展）
- `GET /api/subway/lines?city=` → 线路与站点
- `GET /api/catalog?...&line=&station=&stage=&school_max=&grade=&hospital_max=&hsr_max=` → 复用现有 `/api/catalog` 增加过滤参数（或返回带 `features` 的条目）
- `GET /api/schools?stage=` / `GET /api/hospitals?grade=` → 明细列表
- `GET /api/poi/{poi_id}/communities?limit=20` → 某学校/医院周边小区 Top20
- `GET /api/commute?fromA=&fromB=&mode=&w=&limit=` → 加权排序（内部先粗筛 + 缓存）
> 保持 `/api/overview`、`/api/xiaoqu*` 既有行为不变。

---

## 8. 非功能要求
- **零依赖优先**：P1/P2 的距离计算用 Python 离线预计算（Haversine + 点到折线 + 网格预筛）；不引入第三方框架。
- **性能**：宽表查询 P95 < 200ms；距离预计算离线跑一次即可。
- **成本**：P3 路径 API 必须「粗筛 + 缓存 + 配额上限」，禁止全量实时。
- **可移植**：数据与脚本入 `data/`、`scripts/`，clone 后可重建。
- **合规**：POI/路径 API 遵守 ToS 与展示条款；标注数据来源与「直线距离≠实际通勤」。

## 9. 待确认（阻塞项）
1. **POI 与路径 API**：用高德还是百度？需提供 Key 或授权申请（P2/P3）。
2. **重点校名单**：学校“好坏/重点”需要外部名单，否则排名只有距离。
3. **城市范围**：是否只北京+天津（当前）；扩城市需坐标与 POI 全量。
4. **通勤口径**：均衡模式用「加权均值」还是「最小化最大值」？建议默认加权均值，UI 注明。
