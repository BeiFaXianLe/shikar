# shikar（狩鹿）· 产品需求文档（PRD）

> 产品：**shikar** —— 北京 / 天津 二手房 **小区级趋势与温度看板**（网页端）
> 版本：v0.1（2026-11-06）｜阶段：Phase 1 · 产品设计
> 一句话：**把每个小区的行情，压成一个可解释的「温度」+「阶段」+「右侧信号」，让普通人在买房/卖房前有据可依。**

---

## 1. 产品目标与成功标准

### 1.1 目标
- 帮用户回答三个问题：**这个小区现在「冷还是热」？在「哪个阶段」？「该关注还是该出手」？**
- 用小区级颗粒度 + 可解释指标，替代「只看均价涨跌」的粗糙判断。

### 1.2 成功标准（MVP）
| 指标 | 目标 |
|---|---|
| 覆盖小区 | 北京 ≥ 8,000、天津 ≥ 4,000（可查询、有温度） |
| 数据新鲜度 | 周更，滞后 ≤ 10 天 |
| 温度算法可解释 | 每档温度都能下钻到 4 个分项 |
| 核心页可用性 | 首页→城市→小区 ≤ 3 次点击到达 |
| 用户验证 | 内测 ≥ 20 人，>60% 认为「比只看均价有用」 |

---

## 2. 用户与用户故事

- **购房者**：作为购房者，我想查某小区的温度和阶段，判断现在是不是买入时机。
- **卖房业主**：作为业主，我想知道同小区去化率和议价空间，帮助我定价。
- **经纪人**：作为经纪人，我想拿温度曲线给客户做沟通素材。
- **投资客**：作为投资客，我想看「升温最快」的板块/小区，找右侧机会。

---

## 3. 范围（Scope）

### 3.1 In Scope（MVP）
- 城市：**北京、天津**
- 层级：城市 → 区 → 板块 → **小区**
- **数据档位（固定 B 档）**：仅**小区级聚合指标**（均价、在售套数、成交套数、关注数等数值），不含逐套成交明细、不含房源图片/描述
- 核心：温度、趋势阶段、右侧信号、价格/成交曲线、排行、小区详情
- 辅助：搜索、自选（本地存储）
- **使用形态**：**个人自用、本地部署**（localhost，不公网、不备案、零付费）

### 3.2 Out of Scope（MVP 不做）
- A股 / 大宗商品（趋势动物的多资产，本期不做）
- **逐套成交明细、房源明细/户型图/图片/描述、业主或经纪人联系方式**（合规红线，禁止）
- 交易撮合、贷款计算器、地图 3D
- 预测式「未来房价」（只做情景推演，不做预测承诺）
- 多用户账号体系 / 商业化 / 公网部署

## 5. 页面规格

### P1 · 首页 / 市场温度总览
- 顶部：北京、天津 **城市温度仪表**（0–100，含较上周变化箭头）。
- 中部：**分区温度热力图**（按行政区着色）+ 本周「升温最快 / 降温最快」Top10 板块。
- 底部：指标说明入口 + 数据更新时间 + 免责声明。

### P2 · 城市 / 区 / 板块页
- 面包屑：全国 > 北京 > 朝阳区 > 望京。
- 板块/小区列表：温度、阶段标签、周环比、在售套数、去化率、议价空间。
- 排序/筛选：温度、涨跌幅、成交量、去化率。
- 榜单 Tab：最热 / 最冷 / 升温最快 / 降温最快。

### P3 · 小区详情页（核心）
- 头部：小区名、区/板块、参考均价、在售套数、关注人数、数据日期。
- **温度仪表**：0–100 + 阶段标签（冰点/回暖/升温/过热/降温/下行）+ 较上周变化。
- **温度分解**：动量 / 去化 / 议价 / 热度 四个分项条形（可解释）。
- **历史曲线**：价格（周/月）、成交量柱、在售套数、议价空间（多轴可切换）。
- **信号时间轴**：历史上出现过的「右侧买入 / 风险」信号点 + 触发原因。
- **同板块对比**：与板块均价、邻近 3 个小区的温度对比。
- 免责声明 + 来源标注。

### P4 · 对比页
- 选择 2–4 个小区 → 指标雷达图 + 温度/价格曲线叠加 + 表格对比。

### P5 · 推演页（P1）
- 滑块调整「供给变化 %」「成交变化 %」→ 基于历史弹性估算价格压力方向与区间。
- 明确标注「情景模拟，非预测」。

## 6. 指标与算法定义（可解释、可回测）

### 6.1 基础指标（每小区 × 每周）
| 指标 | 定义 |
|---|---|
| `price` | 挂牌/参考均价（元/㎡） |
| `mom4` | 价格 4 周动量 = price_t / price_{t-4} − 1 |
| `mom13` | 价格 13 周动量 |
| `supply` | 在售套数 |
| `vol30` | 近 30 天成交套数 |
| `absorb` | 去化率代理 = vol30 / supply |
| `bargain` | 议价空间 = 1 − 成交均价 / 挂牌均价 |
| `heat` | 关注人数周增速（如有带看量则合并） |

### 6.2 归一化
- 每个指标在城市范围内做 **52 周滚动百分位**，映射到 0–100，避免量纲与绝对水平干扰。

### 6.3 温度
```
temperature = 0.40*n(mom4) + 0.25*n(absorb) + 0.20*(100 - n(bargain)) + 0.15*n(heat)
```
（权重可在配置中调整；`n()` 为百分位归一化。）

### 6.4 趋势阶段（温度水位 × 动量方向）
| 阶段 | 条件 |
|---|---|
| 冰点 | 温度 < 25 且 mom4 ≤ 0 |
| 回暖 | 温度 < 25 且 mom4 > 0 |
| 温和 | 25 ≤ 温度 < 55 |
| 升温 | 55 ≤ 温度 < 80 且 mom4 > 0 |
| 过热 | 温度 ≥ 80 |
| 降温 | 温度 ≥ 55 且 mom4 < 0 |
| 下行 | 25 ≤ 温度 < 55 且 mom4 < 0 |

### 6.5 右侧信号（示例规则，可回测调参）
- **买入信号**：`price` 站上 13 周均线 且 `vol30` > 近 13 周均值 × 1.2 且 `bargain` 连续 2 周收窄。
- **风险信号**：`price` 跌破 13 周均线 且 `supply` 环比 +15% 且 `absorb` 连续 2 周下降。
- 每个信号必须记录触发时的指标快照（可解释）。

### 6.6 数据字典（核心表）
- `xiaoqu`（小区主数据）：id、city、district、plate、name、alias、lng/lat、建成年份、户数
- `xiaoqu_metric_weekly`：xiaoqu_id、week、price、mom4、mom13、supply、vol30、absorb、bargain、heat、temperature、stage
- `signal_event`：xiaoqu_id、date、type、reason_json
- `source_snapshot`：来源、抓取时间、原始值（用于溯源与重算）

## 7. 非功能需求

- **性能**：首页 P95 < 1.5s；小区详情 P95 < 1s（缓存 + 预计算）。
- **数据**：周更；采集失败自动重试 + 数据新鲜度告警。
- **可用性**：采集断供时降级展示上次数据 + 明确「数据滞后」提示。
- **合规**：不采集个人信息；展示数据来源与时间；页脚「非投资建议」免责。
- **可维护**：数据源 adapter 化；温度权重、阶段阈值配置化。
- **响应式**：移动优先（网页），桌面端支持对比/大图。
- **部署形态**：个人本地运行（localhost），一键启动（Docker Compose 或脚本），零付费、不公网、不备案。
- **合规**：仅存小区级聚合数值，不存个人信息/图片/房源描述；标注来源与「非投资建议」。

## 8. 验收标准（Acceptance Criteria）

1. 输入「北京 望京 某小区」能在 3 次点击内到达详情页，并显示温度、阶段、4 分项、价格/成交曲线。
2. 京津各 ≥ 承诺数量小区有温度值，数据日期可见且滞后 ≤ 10 天。
3. 温度分解四项加总与总分一致（误差 < 0.5），阶段判定与规则一致。
4. 首页两城温度仪表、板块热力图、Top10 榜单正确渲染。
5. 多小区对比（2–4 个）指标与曲线正确叠加。
6. 采集失败时页面给出「数据滞后」提示，不崩。
7. 全站有来源标注与免责声明；无任何个人联系方式数据。
8. 算法口径页可访问，含历史回测样例。

## 10. 依赖与风险
- **强依赖**：合规数据源可用性（见可行性 §3）。数据断了，产品即空壳。
- **算法风险**：需回测避免「玄学」，先做可解释版再优化。
- **范围风险**：小区级数据清洗成本高，务必先建小区主数据表并抽样校核。
